## 二、背景与目标

### 2.1 系统背景

本系统为多券商交易数据聚合平台，核心目标是：

- 将多个境外券商（Schwab、E\*TRADE、Tastyworks）的持仓、订单、成交数据，统一同步到本地数据库
- 通过 REST API 对内部系统提供统一数据查询接口
- 通过 WebSocket 实时推送持仓变更，供前端展示

### 2.2 当前阶段范围

- 仅支持**美股**市场
- 股票代码统一格式为标准代码（如 `AAPL`），不含前缀（`US.`）或后缀（`.US`）
- 系统由单一后端实例运行，暂无多租户需求

## 三、核心功能需求细则

### 3.1 用户认证模块

| 细则编号 | 细则内容 |
|----------|----------|
| AUTH-01 | 系统提供 `/api/v1/auth/login` 接口，接受用户名/密码，返回 JWT Access Token 及 Refresh Token |
| AUTH-02 | 系统提供 `/api/v1/auth/refresh` 接口，接受有效 Refresh Token，返回新 Access Token |
| AUTH-03 | JWT Access Token 有效期默认 1 小时，Refresh Token 有效期默认 7 天 |
| AUTH-04 | Refresh Token 使用后立即加入 Redis 黑名单，防止重复使用 |
| AUTH-05 | 刷新 Token 操作使用 Redis 分布式锁（SETNX，TTL 3 秒），防止并发刷新竞争 |
| AUTH-06 | 登录失败次数超过阈值（默认 5 次/5 分钟）后，对 IP+用户名 组合进行锁定（默认 15 分钟） |
| AUTH-07 | 锁定状态下继续登录返回 HTTP 429，响应体包含 `TOO_MANY_REQUESTS` 错误码 |
| AUTH-08 | 登录接口从 `X-Forwarded-For`、`X-Real-IP`、`RemoteAddr` 中依次获取客户端 IP |

### 3.2 持仓与组合查询

| 细则编号 | 细则内容 |
|----------|----------|
| PORTFOLIO-01 | 提供 `GET /api/v1/portfolio/positions` 接口，返回当前登录用户的全部持仓 |
| PORTFOLIO-02 | 持仓接口支持可选查询参数 `accountId`（按券商账户过滤）和 `symbol`（按股票代码过滤） |
| PORTFOLIO-03 | 提供 `GET /api/v1/orders` 接口，支持按订单状态过滤、分页（`paginated=true`）或全量（`paginated=false`）返回 |
| PORTFOLIO-04 | 提供 `GET /api/v1/trades` 接口，支持按 `brokerName` 过滤 |
| PORTFOLIO-05 | 所有查询接口均需 JWT 认证，仅返回当前登录用户的数据 |

### 3.3 WebSocket 实时推送

| 细则编号 | 细则内容 |
|----------|----------|
| WS-01 | 系统提供 WebSocket 端点 `/ws`（SockJS 兼容），消息代理主题为 `/topic/positions` |
| WS-02 | 每 30 秒（可配置）向所有已连接客户端广播全量持仓列表 |
| WS-03 | 当特定用户持仓发生变更时，调用 `pushPositionsForUser(userId)` 触发推送 |
| WS-04 | 触发式推送采用**防抖**机制（500ms），连续触发只执行最后一次，避免频繁推送 |
| WS-05 | WebSocket 允许来源通过 `app.cors.allowed-origins` 配置，禁止使用通配符 `*` |

### 3.4 券商数据同步

| 细则编号 | 细则内容 |
|----------|----------|
| BROKER-01 | 系统定期（默认每 5 分钟，可配置）从已配置的券商账户同步持仓、订单、成交数据 |
| BROKER-02 | 同步任务支持多账户**并行执行**（`CompletableFuture.allOf`），使用 `brokerTaskExecutor` 线程池 |
| BROKER-03 | 单账户同步失败不影响其他账户，异常仅记录日志 |
| BROKER-04 | 已同步数据持久化至本地 MySQL，供 API 查询 |
| BROKER-05 | 同步账户列表通过 `app.broker-sync.accounts` 配置，支持多账户、多券商映射 |

### 3.5 断路器与重试

| 细则编号 | 细则内容 |
|----------|----------|
| CB-01 | 所有对外券商 API 调用（`getPortfolio`、`getOrders`、`getTrades`）受 Resilience4j 断路器保护 |
| CB-02 | 断路器配置：滑动窗口 10 次、失败率阈值 50%、打开等待 30 秒、半开探测次数 3 次 |
| CB-03 | 断路器打开时优先返回 Redis 缓存数据；若缓存为空，portfolio 抛出 503，orders/trades 返回空列表 |
| CB-04 | 重试配置：最多 3 次、初始等待 1 秒、指数退避倍率 2.0，仅对 `BrokerApiException` 重试 |
| CB-05 | 断路器指标自动暴露至 Micrometer，可通过 `/actuator/health` 查看状态 |
| CB-06 | 每次券商 API 调用通过 `Timer.record()` 记录响应耗时，标签包含 `type`（portfolio/orders/trades）和 `broker`（券商名称） |

### 3.6 券商健康检查

| 细则编号 | 细则内容 |
|----------|----------|
| HEALTH-01 | 为 Schwab、E\*TRADE、Tastyworks 各实现独立的 `HealthIndicator`，注册至 Spring Actuator |
| HEALTH-02 | 健康检查通过调用 `getPortfolio("health-check-account")` 验证连通性 |
| HEALTH-03 | Mock 模式下跳过实际调用，直接返回 UP 状态 |
| HEALTH-04 | 连接失败时返回 DOWN，并附带异常信息 |

## 四、非功能需求细则

### 4.1 安全性

| 细则编号 | 细则内容 |
|----------|----------|
| SEC-01 | 敏感信息（数据库密码、券商 API Key、JWT 密钥）**不得**硬编码或存入 Git |
| SEC-02 | 生产环境敏感信息通过系统环境变量或 Docker Secret 注入，配置文件使用 `${ENV_VAR}` 占位符 |
| SEC-03 | CORS 允许来源通过 `app.cors.allowed-origins` 配置（如 `http://localhost:3000`），禁止通配符 |
| SEC-04 | 所有非认证接口均需 Bearer Token 鉴权（`SecurityConfig` 配置） |
| SEC-05 | 日志中的 `password`、`token`、`secret`、`apiKey` 字段值自动脱敏（`MaskingConverter`） |

### 4.2 可观测性

| 细则编号 | 细则内容 |
|----------|----------|
| OBS-01 | 每个请求自动注入 `traceId`（来自 `X-Trace-Id` 请求头，或随机生成 UUID），并写入 MDC |
| OBS-02 | 响应 Header 中返回 `X-Trace-Id`，供客户端排查问题 |
| OBS-03 | 所有错误响应体均包含 `traceId` 字段 |
| OBS-04 | 开发环境日志输出带颜色的控制台格式（含 traceId），生产环境输出 JSON（Logstash 格式） |
| OBS-05 | 券商 API 不可用时，响应 Header 包含 `Retry-After: 30` |

### 4.3 配置管理

| 细则编号 | 细则内容 |
|----------|----------|
| CONF-01 | 多环境配置文件：`application-dev.yml`（开发）、`application-prod.yml`（生产） |
| CONF-02 | 生产环境 Flyway 强制 `baseline-on-migrate: false`、`out-of-order: false`，防止数据库意外迁移 |
| CONF-03 | `app.cors.allowed-origins` 配置 CORS 允许来源 |
| CONF-04 | `app.rate-limit.login.*` 配置登录频率限制参数 |
| CONF-05 | `resilience4j.*` 配置断路器与重试策略 |

### 4.4 容器化与 CI/CD

| 细则编号 | 细则内容 |
|----------|----------|
| DOCKER-01 | Dockerfile 采用多阶段构建：Maven 构建阶段 + Alpine JRE 运行阶段 |
| DOCKER-02 | 容器以非 root 用户（UID 1001）运行，遵循最小权限原则 |
| DOCKER-03 | JVM 启动参数包含 `-XX:+UseContainerSupport`、`-XX:MaxRAMPercentage=75.0` |
| DOCKER-04 | GitHub Actions 在 `push/PR` 时自动运行测试（含 MySQL、Redis 服务容器） |
| DOCKER-05 | 测试覆盖率通过 JaCoCo 检查（指令覆盖率 ≥ 70%，分支覆盖率 ≥ 60%） |
| DOCKER-06 | 打 `v*.*.*` 标签时自动构建 Docker 镜像并推送至 GitHub Container Registry（GHCR） |

## 五、数据库设计要点

### 5.1 核心设计决策

| 决策编号 | 决策内容 |
|----------|----------|
| DB-01 | 使用 Flyway 管理数据库版本迁移，所有表结构变更通过 SQL 迁移脚本管理 |
| DB-02 | 用户表（`users`）、持仓表（`positions`）、订单表（`orders`）、成交表（`trades`）均含 `user_id` 字段，保证数据隔离 |
| DB-03 | 股票代码统一使用标准格式（如 `AAPL`），系统内部通过代码识别股票，券商特有前/后缀在调用层动态拼接 |
| DB-04 | 用户数据采用"按需入库"策略，不预先导入全市场股票数据 |

### 5.2 主要数据表（已实现）

| 表名 | 说明 |
|------|------|
| `users` | 系统用户（用户名、加密密码、角色） |
| `positions` | 用户持仓（账户 ID、股票代码、数量、均价、市值、未实现盈亏、券商名称） |
| `orders` | 委托订单（账户 ID、股票代码、买卖方向、数量、价格、状态、外部订单 ID） |
| `trades` | 成交记录（账户 ID、股票代码、成交价格、成交数量、佣金、外部成交 ID） |

## 六、券商集成规范

### 6.1 统一接口约定

所有券商实现 `BrokerClient` 接口，提供以下方法：

```
BrokerPortfolio getPortfolio(String accountId)
List<BrokerOrder>  getOrders(String accountId)
List<BrokerTrade>  getTrades(String accountId)
String             getBrokerName()
boolean            isMockEnabled()
```

### 6.2 各券商认证方式

| 券商 | 认证方式 | 实现状态 |
|------|----------|----------|
| Schwab（嘉信） | OAuth 2.0（Authorization Code Flow） | 已完成 |
| E\*TRADE | OAuth 1.0a | 已完成 |
| Tastyworks | Session Token（用户名/密码换取） | 已完成 |

### 6.3 Mock 模式

- 所有券商均支持 Mock 模式（`mock-enabled: true`）
- 开发环境默认开启 Mock，返回预设测试数据，不发起真实 API 调用
- 生产环境必须设置 `mock-enabled: false`

## 二、背景与目标

### 2.1 系统背景

本系统为多券商交易数据聚合平台，核心目标是：

- 将多个境外券商及交易所的账户、持仓、订单和成交数据统一同步到本地数据库；计划接入顺序见第八节
- 通过 REST API 对内部系统提供统一数据查询接口
- 通过 WebSocket 实时推送持仓变更，供前端展示

### 2.2 当前阶段范围

- 仅支持**美股**市场
- 股票代码统一格式为标准代码（如 `AAPL`），不含前缀（`US.`）或后缀（`.US`）
- Binance 是计划中的交易所接入，不代表当前 V1 已支持加密资产；具体 API 产品线、交易市场及资产/订单模型须在开发前确认
- 系统由单一后端实例运行；V1 管理端需按公司/租户 Scope 隔离用户、账户和管理资源（2026-11-20 已确认），这不代表多实例部署
- V1 管理角色与 Scope 基线已确认：平台管理员跨公司、公司管理员限分配公司、风控操作员限分配账户、审计员只读且限授权范围。此决定尚未在当前角色枚举和 Controller 中实现
- V1 响应统一为 `code/message/data`；`code` 使用稳定业务码，HTTP 状态独立表达。错误 `data` 使用 `fieldErrors` 和 `traceId`；后端、Flutter 与 Web 已按协调切换实现，完整回归和部署升级验收仍待完成
- 独立外部 API 客户端凭证不纳入首发，按全栈计划阶段 8 单独评估

## 三、核心功能需求细则

### 3.1 用户认证模块

| 细则编号 | 细则内容 |
|----------|----------|
| AUTH-01 | 系统提供 `/api/v1/auth/login` 接口，接受用户名/密码，返回 JWT Access Token 及 Refresh Token |
| AUTH-02 | 系统提供 `/api/v1/auth/refresh` 接口，接受有效 Refresh Token，返回新 Access Token |
| AUTH-03 | JWT Access Token 有效期默认 1 小时，Refresh Token 有效期默认 7 天 |
| AUTH-04 | Refresh Token 使用后立即加入 Redis 黑名单，防止重复使用 |
| AUTH-05 | 刷新 Token 操作使用 Redis 分布式锁（SETNX，TTL 3 秒），防止并发刷新竞争 |
| AUTH-06 | 登录失败次数超过阈值（默认 5 次/5 分钟）后，对 IP+用户名 组合进行锁定（默认 15 分钟） |
| AUTH-07 | 锁定状态下继续登录返回 HTTP 429 和稳定业务码 `TOO_MANY_REQUESTS`；错误响应遵循统一 `code/message/data` 契约 |
| AUTH-08 | 登录接口只从经过部署配置验证的可信代理链解析客户端 IP；未配置可信代理时使用连接对端地址，不得直接信任任意 `X-Forwarded-For` 或 `X-Real-IP` |

**现状/部署要求**：认证限流与 API 审计已共用 `ClientIpResolver`，仅从配置的可信代理 CIDR 接受代理链；默认不信任任何转发头，非法或歧义的 `X-Forwarded-For` 回退到连接对端。生产环境必须由运维通过 `APP_SECURITY_TRUSTED_PROXIES` 设置实际代理 CIDR，并确保边缘代理清理客户端伪造头；未配置时经代理访问的请求会共用代理对端地址进行限流。IPv4/IPv6、伪造头与异常链已有定向测试。`RequestTracingFilter` 已校验 `X-Trace-Id` 白名单并先于 Spring Security 执行；Security 401/403 和全局业务异常响应均将相同 trace ID 写入响应头与错误体，缺少 MDC 时生成安全 ID，定向测试通过。

### 3.2 持仓与组合查询

| 细则编号 | 细则内容 |
|----------|----------|
| PORTFOLIO-01 | 提供 `GET /api/v1/portfolio/positions` 接口，返回当前登录用户的全部持仓 |
| PORTFOLIO-02 | 持仓接口支持可选查询参数 `accountId`（按券商账户过滤）和 `symbol`（按股票代码过滤） |
| PORTFOLIO-03 | 提供 `GET /api/v1/orders` 接口，支持按订单状态过滤、分页（`paginated=true`）或全量（`paginated=false`）返回 |
| PORTFOLIO-04 | 提供 `GET /api/v1/trades` 接口，支持按 `brokerName` 过滤 |
| PORTFOLIO-05 | 所有查询接口均需 JWT 认证，仅返回当前登录用户的数据 |

### 3.3 WebSocket 实时推送

| 细则编号 | 细则内容 |
|----------|----------|
| WS-01 | 系统提供 WebSocket 端点 `/ws`（SockJS 兼容），消息代理主题为 `/topic/positions` |
| WS-02 | 每 30 秒（可配置）向所有已连接客户端广播全量持仓列表 |
| WS-03 | 当特定用户持仓发生变更时，调用 `pushPositionsForUser(userId)` 触发推送 |
| WS-04 | 触发式推送采用**防抖**机制（500ms），连续触发只执行最后一次，避免频繁推送 |
| WS-05 | WebSocket 允许来源通过 `app.cors.allowed-origins` 配置，禁止使用通配符 `*` |

### 3.4 券商数据同步

| 细则编号 | 细则内容 |
|----------|----------|
| BROKER-01 | 系统定期（默认每 5 分钟，可配置）从已配置的券商账户同步持仓、订单、成交数据 |
| BROKER-02 | 同步任务支持多账户**并行执行**（`CompletableFuture.allOf`），使用 `brokerTaskExecutor` 线程池 |
| BROKER-03 | 单账户同步失败不影响其他账户，异常仅记录日志 |
| BROKER-04 | 已同步数据持久化至本地 MySQL，供 API 查询 |
| BROKER-05 | 同步账户列表通过 `app.broker-sync.accounts` 配置，支持多账户、多券商映射 |

### 3.5 断路器与重试

| 细则编号 | 细则内容 |
|----------|----------|
| CB-01 | 所有对外券商 API 调用（`getPortfolio`、`getOrders`、`getTrades`）受 Resilience4j 断路器保护 |
| CB-02 | 断路器配置：滑动窗口 10 次、失败率阈值 50%、打开等待 30 秒、半开探测次数 3 次 |
| CB-03 | 断路器打开时优先返回 Redis 缓存数据；若缓存为空，portfolio 抛出 503，orders/trades 返回空列表 |
| CB-04 | 重试配置：最多 3 次、初始等待 1 秒、指数退避倍率 2.0，仅对 `BrokerApiException` 重试 |
| CB-05 | 断路器指标自动暴露至 Micrometer，可通过 `/actuator/health` 查看状态 |
| CB-06 | 每次券商 API 调用通过 `Timer.record()` 记录响应耗时，标签包含 `type`（portfolio/orders/trades）和 `broker`（券商名称） |

### 3.6 券商健康检查

| 细则编号 | 细则内容 |
|----------|----------|
| HEALTH-01 | 为每个实际启用的券商/交易所 Adapter 实现独立的 `HealthIndicator`，注册至 Spring Actuator；后续接入顺序见第八节 |
| HEALTH-02 | 使用该 Adapter 的只读健康检查验证连通性；不得通过下单等写操作探测健康状态 |
| HEALTH-03 | Mock 模式下跳过实际调用，直接返回 UP 状态 |
| HEALTH-04 | 连接失败时返回 DOWN，并附带异常信息 |

## 四、非功能需求细则

### 4.1 安全性

| 细则编号 | 细则内容 |
|----------|----------|
| SEC-01 | 敏感信息（数据库密码、券商 API Key、JWT 密钥）**不得**硬编码或存入 Git |
| SEC-02 | 生产环境敏感信息通过系统环境变量或 Docker Secret 注入，配置文件使用 `${ENV_VAR}` 占位符 |
| SEC-03 | CORS 允许来源通过 `app.cors.allowed-origins` 配置（如 `http://localhost:3000`），禁止通配符 |
| SEC-04 | 所有非认证接口均需 Bearer Token 鉴权（`SecurityConfig` 配置） |
| SEC-05 | 日志中的 `password`、`token`、`secret`、`apiKey` 字段值自动脱敏（`MaskingConverter`） |
| SEC-06 | 管理 API 默认拒绝；每个请求须在服务端校验角色、公司/租户 Scope、目标资源归属及操作权限，不能信任客户端提交的 `companyId`、`userId` 或 `accountId` |
| SEC-07 | 日志脱敏不替代数据最小化；不得记录密码、Token、密钥、完整认证/交易请求或无关账户数据 |

### 4.2 可观测性

| 细则编号 | 细则内容 |
|----------|----------|
| OBS-01 | 每个请求由服务端生成 `traceId`；仅在 `X-Trace-Id` 符合长度和字符白名单时接受上游值，否则生成随机 UUID，并写入 MDC |
| OBS-02 | 响应 Header 中返回同一 `X-Trace-Id`，供客户端排查问题 |
| OBS-03 | 所有 API 错误响应的 `data` 均包含该请求的 `traceId`；认证过滤器、异常处理器及响应头必须使用同一值 |
| OBS-04 | 开发环境日志输出带颜色的控制台格式（含 traceId），生产环境输出 JSON（Logstash 格式） |
| OBS-05 | 券商 API 不可用时，响应 Header 包含 `Retry-After: 30` |

## 七、API 版本规范

### 7.1 统一响应与错误契约

V1 统一响应外层冻结为 `code/message/data`；`code` 是稳定业务码，HTTP 状态码独立表达协议状态。成功码为 `SUCCESS`。本次采用自有客户端协调切换：后端、Flutter 与 Web 使用同一契约发布，不在响应中保留旧字段别名；若存在仍在使用旧格式的已部署客户端，必须先完成升级或另行评审版本兼容方案，再发布新契约。

成功响应示例：

```json
{
  "code": "SUCCESS",
  "message": "请求处理成功",
  "data": {}
}
```

错误响应示例：

```http
HTTP/1.1 400 Bad Request
```

```json
{
  "code": "VALIDATION_ERROR",
  "message": "请求参数校验失败",
  "data": {
    "fieldErrors": [
      {
        "field": "email",
        "code": "INVALID_FORMAT",
        "message": "请输入有效的邮箱地址"
      }
    ],
    "traceId": "f3c1a8e18d6b4c29"
  }
}
```

- 错误 `data` 固定为对象，包含 `fieldErrors` 数组（无字段错误时为空数组）和服务端生成/验证的 `traceId`。
- 业务码、HTTP 状态映射采用稳定注册表；客户端不得依赖 `message` 文案或猜测旧响应格式。
- 错误响应不得返回拒绝值、凭证、Token、内部堆栈、SQL 或券商原始错误。
- 错误 `data` 固定包含 `fieldErrors`（无字段错误时为空数组）和 `traceId`；每项字段错误包含稳定的 `field/code/message`。客户端不得将本地化 `message` 作为逻辑分支依据。
- 当前注册表以已有 `ErrorCode` 名称及 HTTP 状态为兼容基线；`TOO_MANY_REQUESTS` 保持原名，不改名为建议性的 `RATE_LIMITED`。语义相似的现有代码也暂不合并，以免破坏已依赖的业务码。

| HTTP 状态 | 稳定业务码 |
|-----------|------------|
| 200 | `SUCCESS`（适用于其他成功 2xx 状态时仍保留实际 HTTP 状态） |
| 400 | `VALIDATION_ERROR`、`INVALID_ARGUMENT`、`INVALID_STATE`、`STOCK_NOT_FOUND`、`STOCK_NOT_WHITELISTED` |
| 401 | `UNAUTHORIZED`、`INVALID_CREDENTIALS`、`TOKEN_EXPIRED`、`TOKEN_INVALID`、`REFRESH_TOKEN_EXPIRED` |
| 403 | `ACCESS_DENIED`、`ACCOUNT_RISK_BLOCKED` |
| 404 | `RESOURCE_NOT_FOUND`、`NOT_FOUND`、`ACCOUNT_NOT_FOUND` |
| 409 | `ORDER_RESULT_UNCONFIRMED` |
| 429 | `TOO_MANY_REQUESTS` |
| 500 | `INTERNAL_ERROR` |
| 503 | `BROKER_UNAVAILABLE` |

字段校验码冻结为 `REQUIRED`（必填约束）、`INVALID_FORMAT`（格式约束）、`OUT_OF_RANGE`（范围/长度约束）、`INVALID_VALUE`（其他值约束）。未知异常统一映射为 HTTP 500 / `INTERNAL_ERROR`；认证与授权过滤器分别使用 `UNAUTHORIZED` 和 `ACCESS_DENIED`。

`dto.common.ApiResponse`、`dto.ApiResponse`、FIX Gateway、Spring Security 错误出口及 Flutter/Web 响应解析已按本契约完成代码迁移；Flutter/Web 客户端仍容忍旧版成功包装以支持协调发布期间的存量服务。契约序列化、认证响应、Security/trace ID 定向测试已通过；完整 API 回归及已部署客户端升级验收仍未完成。旧格式不作为后端发布后的兼容回退。

### 7.2 V1 管理角色与资源 Scope 基线

| 角色 | 默认范围与能力 | 禁止/需单独授权 |
|------|----------------|----------------|
| `ROLE_PLATFORM_ADMIN` | 跨公司管理公司、用户、账户和角色等平台管理资源 | 业务数据仍按明确权限和目的读取；不得自我扩大权限或绕过风控/审计；LIVE 配置及其他高风险操作须独立权限与强化验证 |
| `ROLE_COMPANY_ADMIN` | 仅管理服务端分配的公司 Scope 内用户、组和账户绑定 | 不得跨公司、授予平台/风控/审计角色或修改平台配置；请求中的公司 ID 不得扩大 Scope |
| `ROLE_RISK_OPERATOR` | 仅访问明确分配的账户，查看风险状态并执行单独批准的风控操作 | 不得管理用户/账户绑定或授予权限；清仓不纳入首发，其他写操作须单独权限、确认、结果核验和审计 |
| `ROLE_AUDITOR` | 在授权 Scope 内只读查询审计及必要运营信息 | 不得执行任何写操作或读取 Scope 外数据；敏感字段最小化 |

交易用户角色（如 `ROLE_TRADER`）与以上管理角色分开定义。Scope 必须由后端从已认证身份及权威关系解析；角色变更、停用和 Scope 撤销须在后续请求中及时生效。当前 `Role` 枚举仍为 `ROLE_SUPER_ADMIN`、`ROLE_ADMIN`、`ROLE_TRADER`、`ROLE_VIEWER`，不得自动把旧管理员角色升级为新平台级角色；迁移映射由阶段 1/2 设计并审计。

### 7.3 管理端点授权基线与现状差距

| 资源/端点组 | 目标授权基线 | 当前实现证据与差距 |
|-------------|-------------|--------------------|
| `/api/v1/auth/login`、`/api/v1/auth/refresh` | 公开认证入口；限流、审计和输入校验 | 当前允许匿名访问 |
| `/api/v1/auth/me`、`/api/v1/auth/logout` | 必须有效身份；仅操作当前会话 | 当前 SecurityConfig 要求认证 |
| `/api/v1/trade/**`、`/api/v1/portfolio/**`、`/api/v1/orders`、`/api/v1/trades` | 已认证交易用户；仅访问当前用户绑定且获授权账户；写请求执行风控、幂等与审计 | 当前要求认证；公司/租户 Scope 和所有资源归属仍需逐端点验收 |
| `/api/v1/watchlist/**` | 已认证用户；列表归属只由当前主体决定 | Controller 有查询/添加/删除；需验收跨用户隔离 |
| `/users/**` | 平台管理员跨公司；公司管理员限本公司且仅管理低权限用户 | Controller 当前仅区分 `ADMIN`/`SUPER_ADMIN`，没有公司 Scope |
| `/api/v1/admin/companies/**` | 平台管理员管理公司；公司管理员只读其自身公司信息 | Controller 当前仅区分 `ADMIN`/`SUPER_ADMIN`，列表/详情没有可验证的租户 Scope |
| `/admin/broker-accounts/**` | 平台管理员跨公司；公司管理员只管理本公司授权账户/绑定 | Controller 当前仅区分 `ADMIN`/`SUPER_ADMIN`，没有公司或账户 Scope |
| `/admin/orders/**`、`/admin/positions/**`、`/admin/audit/**` | 平台管理员、公司管理员、风控操作员和审计员分别按其 Scope/职责读取；仅独立授权的角色可执行写操作 | Controller 当前统一使用 `ADMIN`/`SUPER_ADMIN`；查询隔离与字段最小化未验收 |
| `/admin/risk/**` | 风控操作员仅对分配账户执行获批动作；平台/公司管理员不因管理角色自动获得风控写权限；审计员只读 | Controller 当前统一使用 `ADMIN`/`SUPER_ADMIN`；服务端状态变更/清仓仍须按阶段门保持拒绝或暂停 |
| `/admin/brokers/configs/**` | 平台管理员且具备独立配置权限；敏感修改需强化验证和审计 | 当前 `ADMIN`/`SUPER_ADMIN` 管理端点尚未拆分配置权限 |

上述为 V1 目标基线，不代表已实现。所有未明确列出的写端点默认拒绝；阶段 1/2 必须形成按 HTTP 方法、资源、角色、Scope、操作条件和拒绝响应拆分的逐端点矩阵，并在隔离测试中覆盖未认证、错误角色、跨公司/账户、停用用户及并发/重复写请求。

| 细则 | 内容 |
|------|------|
| VERSION-01 | 所有对外 REST API 统一使用 `/api/v1/` 前缀 |
| VERSION-02 | 认证接口路径：`/api/v1/auth/**` |
| VERSION-03 | 业务接口路径：`/api/v1/portfolio/**`、`/api/v1/orders`、`/api/v1/trades` |

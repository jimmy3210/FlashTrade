# FlashTrade 全栈产品化开发计划

**状态**：阶段 0 进行中；阶段 1 的角色/Scope 基线已由用户确认，阶段 1/2 公司 Scope 首个后端切片已在工作区并通过定向测试；其余逐端点实现、隔离 DB 证据与数据保留责任仍待落实
**编制日期**：2026-11-07
**目标**：按可交付、可测试、可安全运营的顺序，把 FlashTrade 建设为在隔离测试环境可端到端使用的产品。当前开发阶段仅使用本地/隔离环境的 Mock；不连接任何真实券商、外部 API 或真实账户，不发送真实订单。

## 1. 目标版本与交付原则

### 1.1 首发产品

首发版本由以下产品部分共同组成：

| 产品部分 | 模块 | 首发职责 |
|---|---|---|
| 交易客户端 | `flash-trade-app`（Flutter） | 用户认证、行情、自选、下单、订单/持仓和账户上下文；首发沿用现有深色主题 |
| Web 管理端 | `flash-trade-web`（Vue 3） | 管理员/获授权运营人员的用户、账户绑定、订单/持仓监控、审计及已确认纳入首发的风控操作 |
| 后端 API | `flash-trade-api`（Spring Boot） | 认证、授权、交易业务规则、风险校验、限流、审计、持久化和统一 API |
| 券商模拟服务 | `flash-trade-mock` | 确定性模拟行情、账户和交易响应；提供错误与超时场景 |
| 数据与运行环境 | MySQL/Flyway、Redis 及部署配置 | 业务持久化、迁移、缓存/协调及环境运行保障 |

Flutter 是交易用户端，Vue 是 Web 管理端；客户端只能经由后端 API 访问业务，不得直连券商或数据库。券商差异封装在后端 Adapter。服务端授权是最终安全边界，前端路由和按钮控制不能替代后端鉴权。

### 1.1.1 前后端职责与边界安全规则

- 前端或 BFF 负责页面呈现、交互和必要的请求编排；Java API 是业务规则、授权、风控和持久化的权威边界。任何请求都须由后端独立校验身份、角色、租户 Scope、资源归属、输入、风险和审计，不因来源是自有 UI/BFF、内网或可信域名而跳过校验。
- 若未来引入 Next.js/BFF/SSR 或其他服务端渲染层，不因此改变现有职责分工，也不默认迁移技术栈。须先评估威胁模型、部署/维护能力和接口契约；薄前端或不直连数据库只能缩小部分攻击面，不能据此宣称整体安全性自动更高。
- SSR/API 代理仅返回页面需要且调用者有权读取的 DTO。服务端密钥、内部配置、其他用户数据和未授权字段不得进入 HTML、客户端 props/hydration payload、浏览器存储或错误响应。含用户身份的数据必须禁用共享缓存，或按用户及 Scope 严格隔离。
- BFF/代理须限制可转发的目标、方法、请求头和响应字段，校验/清理代理头；针对 SSRF、CSRF、XSS、缓存污染及跨用户缓存泄漏进行评审。不得在 BFF 增加数据库/券商直连，或复制后端授权与业务规则。
- CORS 是浏览器跨域控制，不是认证或授权；生产环境仅放行明确的可信 Origin。Cookie 会话须有 CSRF 防护及 `Secure`、`HttpOnly`、适当 `SameSite` 属性；Token 不得进入 URL/日志，须定义有效期、刷新和撤销。JWT 本身不提供防重放保证。
- 所有层统一执行错误脱敏、日志脱敏和 trace 关联；不得向客户端泄露 SQL、内部堆栈、秘密或无权数据。前端校验仅用于及时反馈，后端仍须重新校验。

### 1.2 可用产品的完成定义

首发不是“页面存在”或“接口返回成功”，而是必须同时满足：

1. 用户能在 mock/test 环境完成登录、查看账户和行情、管理自选、提交订单、查询订单与持仓；订单状态和失败原因真实可见。
2. 管理员能在授权范围内完成首发管理工作流，操作有权限检查、审计记录和明确结果。
3. API、Flutter、Web、数据库迁移和 Mock 使用同一业务契约，关键流程有自动化测试。
4. 下单、撤单、账户切换及管理高风险操作保留服务端校验、幂等/重复提交控制和审计；不确定的交易结果不会被 UI 自动重试。所有交易调用仅到 Mock，不连接外部券商 API。
5. 数据库迁移可在隔离环境验证新建和升级；不会通过修改已执行的 Flyway 脚本解决问题。
6. Flutter 首发沿用现有深色主题；交易信息清晰可读、可操作。主题系统与节日皮肤延期，不作为 V1 验收门。
7. 未执行的测试、未实现的规划能力和未验证的生产行为均明确标示，不以占位页面或静态数据冒充完成。

## 2. 范围基线与优先级

### 2.1 首发 Must

**交易用户**

- 登录、会话恢复/失效、登出。
- 查看当前授权账户、账户环境、余额/购买力和持仓摘要。
- 查看和搜索首发券商支持的标的/行情；显示数据时间和不可用状态。
- 自选列表的查看、添加、删除；排序是否首发由现状核验后冻结。
- 订单预览/确认、下单、订单列表/详情、撤单；改单仅在券商及接口契约确认支持后纳入。
- 对加载、空数据、网络错误、权限拒绝、数据过期、券商拒绝和结果未知提供真实状态反馈。

**Web 管理端**

- 管理员认证和受保护路由。
- 首发确认的用户启停/管理、券商账户及用户绑定管理。
- 订单/持仓监控和审计查询。
- 管理操作的权限、Scope、二次确认（适用时）、防重复提交和审计。
- 风控写操作及生产级券商配置只有在产品、服务端保护和测试范围均确认后纳入；否则明确延期，不展示可误用的空操作入口。

**平台**

- 可重复运行的本地/隔离 Mock Adapter 纵向闭环；当前阶段不连接真实券商或任何外部交易 API。
- 统一 API 契约、错误语义、分页和账户归属。
- Flyway 迁移、新库初始化和现有测试版本升级验证。
- 请求日志脱敏、关键操作审计、基础健康检查及隔离测试配置。

### 2.2 Should / Later

Should 默认不阻塞首发：改单、完整 RBAC/Scope 管理 UI、更多管理报表、跨设备同步用户偏好、推送/实时行情等。公司/租户级服务端 Scope 已确认属于首发安全要求，但 Scope 管理 UI 是否首发仍按本条延期。

Later 默认不阻塞首发：外部 API 客户端凭证、主题系统/节日皮肤、多券商同时上线、期权、Level 2、行情图表/Scanner/News、用户自定义任意配色、在线下载第三方皮肤包、未定义的数据分析和业绩报表。

### 2.3 首发决策清单

每项决策必须记录负责人/结论/日期/影响面；未决且阻塞安全或接口契约的项，不得进入相关实现：

1. 当前阶段固定为本地/隔离 Mock，不连接外部 API；真实券商接入须另行确认、授权并进行安全评审。
2. 外部 API 客户端凭证不纳入首发，按阶段 8 单独评估。
3. API 响应契约已冻结为 `code/message/data`，`code` 为稳定业务码；HTTP 状态独立表达，错误 `data` 使用 `fieldErrors` 与服务端生成/验证的 `traceId`。阶段 1 已冻结业务码注册表、HTTP 状态映射及协调迁移策略；后端、Flutter 与 Web 已完成代码迁移，完整 API 回归及已部署调用方升级验收仍待完成。
4. 首发要求公司/租户级 Scope；首发角色类型已确认为平台管理员、公司管理员、风控操作员和审计只读角色。阶段 1 冻结权限、公司/组/用户/账户资源关系、授权矩阵与账户归属规则。所有 Scope 必须由后端从已认证身份解析。
5. 按本计划 Must/Should/Later 基线确定首发能力；新增范围须记录批准与影响，不因代码中已有页面或路由而默认为 Must。
6. 数据库实际 schema、已应用迁移、数据保留和敏感信息存储边界。
7. 首发沿用现有深色主题；主题系统、节日皮肤及相关素材预算延期。
8. UI 偏好默认本地保存；跨设备同步延期，未经重新确认不增加用户设置 API 或数据库字段。

## 3. 后续版本：Flutter 主题与节日皮肤

本节作为后续版本设计输入，不属于 V1 Must 或首发验收门。V1 沿用现有深色主题，不为满足本节新增主题设置或节日素材。

### 3.1 基础视觉套系

- 至少设计并交付两套完整基础款，例如 Dark Terminal（深色交易工作台）与 Light Editorial（浅色信息版）；名称和视觉方向需设计评审确认。
- 每套包含颜色语义、字体家族/字重/数字字形、背景材质或图案、图标语言、组件形态/密度、插图及动效规范。
- 提供 `System`、`Light`、`Dark` 模式；每个基础款都需定义浅色与深色下的完整样式，不允许仅由系统自动反相而产生未经设计的颜色。
- 通过统一 Design Tokens 和组件实现，所有业务页面、弹窗、菜单、表格、输入、状态标签保持一致。

### 3.2 节日皮肤与吉祥物

- 建立节日皮肤系列，按产品确认的目标地区和日历设计相应的主题元素、专属图标/图标状态、背景/插图和原创吉祥物；春节、圣诞节等作为候选，不预设所有地区使用同一节日表。
- 每个节日素材包定义适用基础款、浅/深色变体、生效区间、时区、离线可用方式和版本；节日皮肤可在基础款视觉语言上做季节化表达，但不得破坏可读性。
- 自动启用可关闭；用户手动选择/恢复默认优先级、节日结束后的恢复策略和跨时区行为须明确且一致。
- 吉祥物仅用于登录欢迎区、空状态、设置页等非关键区域；不得遮盖报价、订单确认、账户环境、风险告警和主要操作，也不得被误读为行情/交易信号。
- 字体、图标、插画和吉祥物必须原创或有明确商业分发授权，维护素材来源和授权记录；不使用未经许可的品牌角色或第三方节日素材。

### 3.3 主题验收

- 至少两套基础款及后续版本确定的节日皮肤完成视觉稿、切图/字体清单、组件状态和设计评审。
- 所有皮肤在移动与桌面布局、浅/深色模式、字体回退和系统文本缩放下可用。
- 买卖方向、盈亏、LIVE/SANDBOX、风险和订单状态同时使用文字/图标/形状等非颜色线索表达；关键文本对比度经验证。
- 主题切换即时生效，偏好重启后保持；节日自动启用、关闭、手动覆盖、结束恢复按设计运行。
- 减少动效不会丢失信息或功能；吉祥物/装饰永远不遮挡关键交易路径。

## 4. 数据、API 与安全实施基线

### 4.1 API 与业务服务

- 先冻结 API 契约，再修改 Controller、Service、DTO、Adapter 和客户端调用；变更逐一检查 Flutter、Web、Mock 及获授权 API 消费者。
- 业务规则位于后端服务层。账户绑定、账户状态、主体/Scope、交易环境及风险校验不能信任客户端传入值。
- 交易写操作需明确定义幂等键、重复请求处理、同键异请求拒绝和券商响应未知时的状态查询/人工处理路径。
- 券商不支持的能力返回明确错误/能力状态，不能用静态数据或 success-shaped fallback 伪造成功。
- 所有管理写操作验证角色与目标范围；高风险动作定义二次确认、幂等、防重放、审计和失败恢复方式。

#### 4.1.1 首发角色与 Scope 基线（2026-11-20 用户确认）

| 角色 | 授权范围与能力 | 明确禁止 |
|---|---|---|
| `ROLE_SUPER_ADMIN` | 平台级管理，可跨公司读取和管理资源、查看系统级日志 | 不得由 `ROLE_ADMIN` 或请求参数隐式获得 |
| `ROLE_COMPANY_ADMIN` / 历史 `ROLE_ADMIN` | 仅管理自身明确归属公司的普通用户、券商账户及该公司范围内的运营数据；历史 `ROLE_ADMIN` 无公司 Scope 时默认拒绝 | 不得跨公司、管理平台管理员或授予高于自身的角色；不得创建/删除公司或修改公司级启停状态 |
| `ROLE_RISK_OPERATOR` | 仅读取显式授权账户的风控状态及必要监控数据 | 本阶段所有风控状态写操作继续拒绝 |
| `ROLE_AUDITOR` | 只读显式授权账户/用户关联的审计日志 | 不得读取无资源关联的系统级日志或执行任何写操作 |
| `ROLE_TRADER` / `ROLE_VIEWER` | 保持现有用户自身数据权限，由业务 API 单独校验资源归属 | 不得访问管理端跨用户数据 |

| API 资源组 | `ROLE_SUPER_ADMIN` | 公司管理员 | 风控操作员 | 审计员 |
|---|---|---|---|---|
| `/api/v1/admin/companies/**` | 全部公司；公司级写操作 | 仅读取自身公司；公司创建、删除、启停和跨公司查询拒绝 | 拒绝 | 拒绝 |
| `/users/**` | 全公司用户管理 | 仅本公司普通用户；不能管理特权角色或跨公司用户 | 拒绝 | 拒绝 |
| `/admin/broker-accounts/**` | 全账户管理 | 仅本公司账户及其绑定 | 仅读取显式授权账户 | 拒绝 |
| `/admin/orders/**`、管理员 `/positions` | 全局读取；写操作依具体接口阶段门 | 仅本公司数据 | 仅读取显式授权账户数据 | 拒绝 |
| `/admin/risk/status` | 全局读取 | 仅本公司账户 | 仅读取显式授权账户 | 拒绝 |
| `/admin/risk/{disable,enable,limit,liquidate}`、管理员平仓/撤单 | 按已实现的服务端安全阶段门；当前保持拒绝 | 拒绝 | 拒绝 | 拒绝 |
| `/admin/audit/**` | 全局审计日志（含系统级日志） | 默认拒绝 | 拒绝 | 仅读取与其显式授权资源关联的日志 |
| `/actuator/**` | 仅平台级管理端点 | 拒绝 | 拒绝 | 拒绝 |

实现约束：公司 Scope 从已认证用户的 `users.company_id` 解析；交易账户的公司归属通过 `t_broker_account.user_id` 关联其所有者，不从客户端传入公司 ID 推导。风险/审计账户授权按内部券商账户主键解析；历史 `t_user_scope.target_account_id` 字符串值未经映射与审计不得直接当作授权。`target_user_id`、旧组关系或缺失/不可解析的 Scope 均不得扩大权限。V28 已新增 nullable `users.company_id` 与 `t_user_scope.target_broker_account_id`，不自动回填用户或旧授权；公司管理员用户/账户读取端点已按 Scope 过滤，创建、更新、停用、密码、绑定等写操作暂限平台管理员。用户创建契约尚不能指定公司归属；无公司映射的用户对公司管理员不可见。迁移执行、历史数据映射与完整逐端点拒绝测试仍待阶段 2 完成；不得修改已应用迁移，也不得自动把未映射的 `ROLE_ADMIN` 赋予任何公司或全局权限。

### 4.2 数据库与缓存

- 以目标环境的迁移历史、运行时 schema、实体和数据访问逻辑为准，设计文档只作为目标参考。
- 已应用 Flyway 脚本不可修改；通过新增 migration 实施结构变化，说明约束、索引、金额精度、时区、空值、保留、回填和兼容策略。
- 核验用户/角色/Scope、券商/账户/绑定、订单/成交/修改、持仓、自选、审计及用户设置的实际模型；不得预设规划表已经存在。
- 不因券商 API 可返回就镜像保存全部数据：本系统必须持久化自己的身份/授权、订单意图/状态和必要审计；券商订单 ID、状态变化及成交保存满足查单/对账所需的最小字段。
- 余额、购买力、持仓和行情优先实时读取；只有在性能、离线展示、历史分析或对账有明确需求时才缓存或保存精简快照，并记录来源、采集时间、TTL/过期语义及保留期限。完整原始券商响应和全量行情历史默认不持久化。
- 下单请求超时或响应丢失时，本地记录必须能表达 `UNKNOWN` 等不确定状态并支持后续查单/对账；不得因本地暂时无记录而盲目重试。Redis 可做短期并发协调，但不能作为唯一幂等账本。
- 所有持久化数据均须有分类型保留期限和定期清理/归档策略；具体期限由产品、法务/合规和运维确认，不得默认无限保留。未终结订单、`UNKNOWN` 订单、未完成对账及调查冻结记录不得清理。
- 后端清理任务须可配置、幂等、可重入、分批运行、可暂停并有失败告警；清理需遵守外键/审计关联，记录最小化执行摘要，同时明确备份和副本的独立过期周期。
- MySQL 保存权威业务记录；Redis 只用于明确的缓存/协调用途，不能成为唯一交易账本。
- 主题偏好默认用客户端本地存储，与凭证分离；只有确认跨设备需求后才设计后端同步和 schema。
- 升级/回填测试仅对隔离、可丢弃测试库执行；禁止删除数据库卷或清空非测试数据。

### 4.3 安全与隐私

- 当前开发、联调和验收阶段禁止发起任何外部 API 请求；券商及行情依赖均使用本地/隔离 Mock。不得连接真实账户、提交真实订单或操作生产数据。
- Mock 环境应使用显式配置与虚构账户/行情数据；测试不得读取生产凭证或在 Mock 不可用时回退到真实 Adapter。
- 在阶段 0–7 及其验收期间，外部券商 API 总开关保持关闭；管理端数据库配置不得覆盖此限制或切换到 SANDBOX/PRODUCTION。
- 真实券商 API 的启用必须作为后续独立变更，取得用户明确授权并完成配置隔离、安全评审和专项验收；本计划不默认包含此启用。
- 密码只存哈希；券商凭证、JWT 密钥、Token 和账户敏感数据不暴露在前端、不写入普通日志或仓库。
- 认证、授权、账户归属、风控、限流、审计和幂等都须有后端保护与测试证据。
- 外部客户端凭证、生产券商配置和 LIVE 操作若非首发，必须在页面、API 和配置中明确禁用，而不是仅靠文档提示。

### 4.4 系统日志、监控与告警

- 将运行日志、API 访问日志、安全/管理审计、交易业务事件和监控指标分开定义；日志用于诊断，审计用于追责，指标用于趋势和告警，不要求全部写入业务数据库。
- 后端与 Mock 输出结构化日志，统一 UTC 时间、服务/环境/版本、事件名、级别和 `traceId`/`requestId`；trace ID 从 API 入口贯通至服务、订单状态事件和后台作业。
- 重点记录认证/授权拒绝、账户归属校验、订单状态变迁、幂等冲突、`UNKNOWN`、对账差异、管理写操作、清理任务、数据库/Redis/线程池故障；记录有助于排查的 ID、耗时、结果分类和错误码。
- 建立请求错误率/延迟、依赖健康、资源容量、待处理任务和数据清理结果等指标；限制标签基数，避免用用户/账户 ID 作为时序指标标签。
- 定义 Critical/High/Medium/Info 分级、去重/抑制、恢复通知、升级对象和响应时限；具体数值阈值由运行基线与风险评审确定。
- 当前开发验收阶段仅使用本地日志/监控和测试告警接收器；禁止连接外部交易 API、真实券商或外部通知服务。通知渠道若要接入，须另行确认授权。
- 日志和告警不得包含密码、Token、密钥、完整账户凭证或完整订单请求；日志采集失败、审计写入失败、磁盘满及日志过期清理均须有明确降级、监控与告警策略。

### 4.5 网络攻击防护基线

- 在入口层部署 TLS、网络边界规则和适用的 WAF / DDoS 防护；网络层限速不能代替上游抗大流量攻击能力。管理端、API、数据库、Redis 按最小暴露面部署，数据库和 Redis 不得直接暴露公网。
- IP 策略分层实施：服务器/云防火墙/WAF 负责入口准入、恶意流量拦截和 DDoS 缓解；应用系统负责可信来源解析、统一限流、攻击检测、审计和有 TTL 的临时封禁。应用不得直接修改服务器防火墙规则。
- 系统级策略由系统安全设置统一管理，覆盖全局封禁、管理员入口来源限制、默认限流/阻断和可信代理配置；公司级策略由公司详情的“安全与 IP 访问”设置维护该公司办公/开发出口 CIDR，仅约束已认证且已绑定该公司的会话或 API/MCP 客户端。公司管理员自助管理权限须另行评审，未批准前由平台管理员操作并审计。
- 全局封禁优先于所有来源允许名单；公司白名单仅为附加访问限制，不能豁免系统规则、替代认证/MFA/授权、绕过账户归属或跨租户访问。公司 Scope 必须从已认证身份解析，禁止仅凭请求参数选择租户。公司规则采用规范化 IPv4/IPv6 CIDR，拒绝过宽范围并定期复核。
- 对登录、Token/密码重置、管理写操作、交易写操作和昂贵查询实施分层限流，按来源 IP、账号/主体、路由和全局容量联合判断；用共享/分布式计数避免多实例各自限流造成的绕过。高风险管理操作要求 MFA 或重新认证的产品决策须在范围冻结时确定。
- 设计自动 IP 限制：对短时间认证失败突增、明确的扫描/攻击特征或多信号高置信异常，先按规则限速，达到经批准阈值后立即施加有 TTL 的临时阻断并触发告警；封禁范围、阈值、时长和升级策略须可配置、可审计，自动封禁默认不得永久化。
- IP 判定只能使用网络边界可信代理传递的客户端地址；入口应移除外部伪造的转发头，只信任明确配置的代理链。覆盖 IPv4/IPv6、负载均衡和多实例，禁止直接信任任意 `X-Forwarded-For`。
- 为避免误封和管理锁死，支持受控的受信来源/紧急恢复通道、封禁到期自动解除、人工解除/延长及变更审计；允许名单必须最小化、定期复核，不能成为绕过认证授权的通行证。对共享 NAT 的误伤风险应优先采用账号/IP 联合判定和端点级限制。
- 对登录实施账号与来源双维度的渐进式延迟/临时锁定，结合 MFA、密码哈希和会话撤销；不向未认证请求泄露账号是否存在。验证码/挑战仅作为经评估的补充控制，不能替代限流。
- 全面执行身份认证和服务端授权、对象归属校验、输入校验/输出编码、参数化查询、CSRF/CORS 和安全响应头策略；限制上传文件类型/大小，防止注入、越权、XSS、CSRF、SSRF、路径穿越及资源耗尽。
- 凭证采用最小权限、独立环境、加密/密钥管理和轮换；减少管理员权限并启用 MFA。依赖与构建产物执行漏洞/许可证扫描，保护 CI/CD 权限和发布链路；备份需隔离、限制访问并定期验证恢复。
- 建立攻击响应流程：告警后可快速限制来源、撤销会话/令牌、暂停受影响写操作、隔离服务并保全审计证据；应急操作需双人/授权控制（适用时）和事后复核。阈值、SLA 与封禁时长待安全评审和基线测试确定。
- 自动封禁与限流的验收须覆盖伪造转发头、可信代理链、IPv4/IPv6、共享出口误伤、跨实例计数、全局封禁优先级、公司间白名单隔离、错误/过宽 CIDR 拒绝、封禁到期/人工解除、受信恢复路径及计数存储故障；当前仅在本地/隔离环境验证。

**阶段门**

- 管理工作流在 mock/test 环境可用；TRADER 不能通过 API 或 UI 获取管理数据。
- 管理 Scope 在后端强制执行；敏感配置不回显。
- `npm run build` 通过，构建产物差异已检查。

### 阶段 6：跨端集成、安全回归与发布候选

**执行内容**

- 执行交易用户、管理用户、账户授权、自选、订单、审计、异常/超时及数据库升级端到端流程。
- 验证 API 契约和错误状态在 Flutter/Web 一致呈现；执行关键页面截图/golden 或等价回归。
- 检查性能/分页上限、trace 贯通、日志脱敏、审计完整性、限流/IP 临时阻断及解除、可信代理解析、健康检查、告警触发/去重/恢复、备份恢复和配置边界。
- 运行 API `mvn test`、Mock `mvn test`（若改动涉及 Mock）、Flutter `flutter analyze`/相关 `flutter test`、Web `npm run build` 及迁移升级测试。
- 逐项更新追踪矩阵，记录执行命令、环境、结果、失败项和未覆盖项。

**交付物**

- E2E/回归报告、缺陷清单、验收追踪矩阵和发布候选构建。

**阶段门**

- 所有 Must 验收通过或有经批准的延期/风险说明；无未解决的越权、重复下单、数据迁移破坏或交易结果误报。
- 测试失败和未执行项透明记录，不能以构建通过代替端到端验收。

### 阶段 7：文档、发布准备与后续运营

**执行内容**

- 更新产品功能/页面说明、API 契约、DB 数据字典/migration、Flutter 深色 UI 基线、管理手册和运维排障说明。
- 更新日志字段字典、关键事件/告警规则、日志保留和访问权限、告警响应/升级及排障手册。
- 确认配置、部署、监控、备份、回退和支持流程；发布候选仅在 mock/test 环境验收且外部 API 保持禁用。
- 真实券商/生产环境启用必须另立授权、风险审批、操作步骤和回退计划，不自动属于首发完成。
- 建立节日素材的后续版本制作/审查/发布时间流程，不在运行时下载未经验证的素材。

**阶段门**

- 产品、代码、API、DB、运行手册与实际发布版本一致；遗留问题和不支持能力可追踪。
- 无生产凭证进入仓库、日志或普通测试环境；未获授权不操作真实账户或订单。

### 阶段 8：外部券商 API Adapter（首发后独立阶段）

仅在阶段 0–7 的核心 Mock 闭环通过验收、并获得单独授权后启动。本阶段不属于首发发布门。

**执行内容**

- 按券商逐一实现 Adapter；复用已冻结的统一领域/API 契约，不将券商差异泄露给 Flutter、Web 或业务服务。
- 将外部 API 凭证、网络目标、环境和账户严格隔离；默认先接入券商 Sandbox，配置与本地 Mock/test 完全分离。
- 补齐认证/令牌生命周期、请求限制、错误映射、超时/结果未知、幂等查单、审计/脱敏、告警及断路器行为。
- 每家券商分别进行契约、授权隔离、失败场景和 Sandbox 端到端验收；生产连接需额外授权、风险审批、回退方案和专项验收。

**阶段门**

- 未启用明确授权的外部环境时，所有请求仍由本地 Mock 处理；Mock 故障不得回退到外部 API。
- Sandbox 验收通过且生产审批单独完成前，不允许连接真实账户或发送真实订单。

## 6. 依赖关系与并行安排

1. 阶段 0 冻结范围并建立差距/追踪基线。
2. 阶段 1 冻结产品流程、公司/租户权限 Scope、API 与 DB 契约。
3. 阶段 2 先形成认证、账户授权、幂等与 mock/test 基础；阶段 3 在此基础上实现纵向 API 闭环。
4. 阶段 4 和阶段 5 可并行，但依赖阶段 1 的冻结契约和阶段 3 可联调的 API；允许先用 Mock 并行开发页面。
5. 阶段 6 依赖 API、Flutter、Web、DB 与 Mock 达到集成候选状态；阶段 7 依赖验收门通过。
6. 阶段 8 只能在阶段 7 完成、取得单独授权并通过 Sandbox 准入评审后启动。

按“安全/契约与后端闭环 → Flutter 用户交易闭环 → Web 管理 Must → 增强运营能力”的顺序切片发布。主题系统与节日皮肤作为后续版本，不阻塞 Flutter 首发验收。

## 7. 主要风险与应对

| 风险 | 影响 | 应对/阶段门 |
|---|---|---|
| 设计、代码、API 与 DB 文档不一致 | 返工或跨端行为不一致 | 阶段 0 形成差异决议与追踪矩阵 |
| 账户归属、幂等或券商超时处理不足 | 越权或重复交易 | 阶段 2 安全门未通过前不开放相关交易写能力 |
| 外部券商未接入 | 真实券商流程不能在当前阶段验证 | 当前首发以 Mock 验证统一契约；外部接入另行授权和评审 |
| 迁移历史与建议表不一致 | 部署失败/数据损坏 | 依据实际迁移与 schema 设计新迁移，在隔离库升级验证 |
| 后续主题/节日皮肤的多地区日历、时区复杂 | 自动切换错误或用户困惑 | 主题功能重新立项时冻结地区/时区与回退策略；不进入 V1 |
| 后续主题素材授权不清 | 法务或发布风险 | 主题功能重新立项时核验字体、图标、插画和吉祥物授权 |
| 视觉装饰影响交易可读性 | 误读数据或误操作 | V1 沿用深色主题并验证关键交易字段可读；主题矩阵留待后续版本 |
| 测试工具链不可用 | 无法验证产品可用性 | 阶段 2 恢复并记录工具链；未执行验证不报告为通过 |
| Web 构建覆盖静态资源 | 意外改变后端交付内容 | 构建前后比较工作区差异并明确输出目录 |

# FlashTrade Web 管理端产品功能、页面与数据库设计

**状态**：设计与实施计划，须按当前代码和数据库环境核实  
**适用模块**：`flash-trade-web`、`flash-trade-api`、MySQL/Flyway  
**目标**：把现有 Vue 管理端、管理 API 和数据库整理为权限清晰、操作可追溯、可在测试环境验收的 Web 管理产品。

## 1. 产品定位与设计原则

Web 管理端面向内部管理员和获授权的风控/运营人员，用于用户与账户管理、持仓/订单监控、风控和审计。它不是面向交易用户的下单终端。

- 管理端只调用 FlashTrade 后端 API，不直连券商，也不直接访问数据库。
- 后端是授权和业务校验的最终边界；隐藏按钮或路由守卫不能代替服务端鉴权。
- 管理写操作必须验证操作者权限、目标范围、目标状态，并记录审计结果。
- 强制平仓、LIVE 环境配置、账户停用等高风险动作应醒目提示、二次确认、避免重复提交，并明确展示执行状态。
- 页面数据需区分实时结果、同步快照和缓存；失败或数据过期时不能展示为成功或最新。
- 保留现有管理端功能；延期项应明确标注，不能以空页面或无效入口冒充已交付。
- 所有账户及交易验证限定在 mock/test 环境。未经明确授权，不连接真实账户、不发真实订单、不操作生产数据。

### 1.1 前端/BFF 与 Java API 安全职责

- Vue 管理端只负责视图、交互和请求编排；Spring Boot API 是身份授权、租户/资源范围、业务校验、风控、审计和数据库持久化的权威边界。所有管理 API 必须逐请求验证身份、角色、Scope、目标资源归属及操作条件，不得信任浏览器传入的用户、账户、公司 ID 或“请求由自家页面发出”这一事实。
- 如未来采用 Next.js、BFF、SSR 或服务端组件，仅作为可选的展示/代理层，须单独评审后引入；不代表本项目已决定迁移。不得直连数据库或券商、复制 Java 服务层规则，亦不得因处于内网而获得隐式业务权限。
- SSR/BFF 仅可返回页面所需且用户有权读取的 DTO；不得把服务端密钥、内部配置、其他用户数据或未授权字段放入 HTML、客户端 props/hydration payload、浏览器存储或错误信息。用户相关响应不得进入未按用户和 Scope 隔离的共享缓存。
- BFF 必须限制上游目标、HTTP 方法、转发头和响应字段，避免成为任意代理；设计时评审 SSRF、CSRF、XSS、代理头伪造、缓存投毒及跨用户缓存泄漏。API 代理不得转发不必要的凭证或完整敏感请求。
- CORS 只约束浏览器跨域访问，不能取代 API 认证/授权。生产环境按部署拓扑精确配置 Origin；Cookie 会话启用 CSRF 防护和 `Secure`/`HttpOnly`/适当 `SameSite` 属性。Token 不放入 URL 或普通日志；须明确有效期、刷新和撤销，不能依赖 JWT 自带防重放。
- 所有 API 错误、SSR 响应和日志均应脱敏，不暴露内部堆栈、SQL、秘密或无权数据。前端路由守卫、隐藏控件和表单校验仅用于 UX，不能作为安全控制。

### 2.3 已知接口/页面对齐问题

- 管理端登录页面、请求封装与后端认证入口需统一；禁止仅凭任意有效用户 JWT 进入管理工作流。
- `PositionManage.vue` 当前读取 `GET /positions`；后端仍同时存在 `GET /admin/positions` 和 `GET /positions`，响应结构不同且尚无细粒度 Scope 过滤。应先定义权威分页/响应契约与授权范围，再收敛重复路由。`POST /positions/close_all` 已由后端拒绝，不能从前端开放。
- 公司管理使用 `/api/v1/admin/companies`，其他管理 API 主要使用 `/admin/**` 或 `/users`，需明确统一 API 前缀/代理策略。
- 审计页面使用 `/admin/audit/**`，后端另有旧 `/admin/logs/**` 端点；确定权威路径和兼容策略，避免双重实现造成日志来源不一致。
- 风控页面已接入；服务端风控状态变更现在拒绝非 ACTIVE、非 SANDBOX 或无法唯一识别的账户，并在审计写入失败时让请求失败。管理员 Scope 仍未实现/核实；强制清仓 API 已关闭，待可靠的异步执行状态、逐账户授权和审计能力完成后再评审开放。
- 管理文档中的“业绩管理”目前是占位，应确认要删除、隐藏还是列入后续版本。

## 3. 管理端功能设计

### 3.1 管理员认证与会话

#### 认证与授权边界

- **认证回答“当前是谁”**：统一认证服务验证凭证、用户启用状态和会话有效性。登录成功不等于获得管理权限；有效的普通交易用户凭证不能因此进入或调用管理功能。
- **授权回答“可以对什么资源做什么操作”**：Java API 是唯一权威授权边界。每个管理 API 请求都必须独立校验有效身份、所需角色/权限、公司/组/账户等 Scope、目标资源归属及操作前置条件；拒绝未明确授权的访问（默认拒绝）。不得把前端提交的用户/公司/账户 ID、菜单状态、来源页面或网络位置当作授权依据。
- 未认证、会话过期或撤销返回 `401`；已认证但角色、权限或 Scope 不足返回 `403`。错误响应不得包含凭证、内部配置、其他用户数据或堆栈信息。
- Vue 路由守卫在加载管理工作流前应取得服务端确认的身份/权限状态：未认证跳转登录；已认证但无管理权限显示无权页面；权限状态尚未确认时保持加载/失败状态，不得默认放行。菜单和按钮按权限隐藏仅用于 UX，不能替代后端校验。
- 登录界面不得通过注册、隐藏字段或客户端参数自行授予管理员权限。管理员身份与角色授予必须走受控的服务端管理流程并写入审计。

#### 角色、权限与资源 Scope

- 授权采用“角色/权限 + 资源 Scope”组合：角色用于授予管理动作，Scope 限制这些动作可作用的公司、组、用户或券商账户。后端应在服务层/数据访问边界落实 Scope，避免只在前端过滤或先读取越权数据再隐藏。
- 当前代码中已使用 `ROLE_ADMIN` 保护部分管理 Controller；此角色是现状，不代表已有细粒度角色或 Scope 授权。新增角色须同步定义后端权限映射、接口策略、数据 Scope、审计和自动化测试，不得只新增前端角色名。
- 首发四类角色及其 Scope 基线已于 2026-11-20 确认。逐端点授权、Scope 继承/组合规则、MFA/step-up 策略和现有角色迁移映射仍须在阶段 1 冻结；当前代码不代表已实现这些角色。

| 职责角色 | 允许的典型能力 | 默认限制 |
|---|---|---|
| `ROLE_PLATFORM_ADMIN` | 平台级跨公司管理公司、用户、账户及角色；处理经批准的平台级运营事务 | 业务数据访问仍须有明确权限和目的；不得绕过资源校验、风控/审计或自行扩大权限；LIVE 配置及其他高风险操作另设权限并要求强化验证 |
| `ROLE_COMPANY_ADMIN` | 仅在明确分配的公司 Scope 内管理获授权用户、组及账户绑定 | 不得跨公司访问、提权或修改平台级安全/券商配置；不得因用户提交公司 ID 扩大 Scope |
| `ROLE_RISK_OPERATOR` | 在明确分配的账户 Scope 内查看风险状态并执行单独批准的风控操作 | 不得默认获得用户/账户管理、权限授予或券商全局配置权限；写操作必须服务端校验、确认及审计 |
| `ROLE_AUDITOR` | 在获授权 Scope 内只读查询审计及运营信息 | 禁止写操作；不得读取 Scope 外数据，敏感字段须最小化 |

- 所有管理角色均受同一服务端身份、Scope、资源归属、状态校验和审计链约束；角色只授予动作，Scope 限制作用对象。
- 当前代码使用 `ROLE_ADMIN`/`ROLE_SUPER_ADMIN` 并包含超级管理员部署引导（`BOOTSTRAP_SUPER_ADMIN_ENABLED`、`BOOTSTRAP_SUPER_ADMIN_USERNAME`）。这是现状，不等于上述四类角色已实现；阶段 1 必须确定兼容/迁移及受控引导方案，未完成前不得开放角色或 Scope 自助变更。
- 角色授予/撤销、LIVE 配置及其他高风险操作须拆分权限、强化验证并完整审计；任何平台级角色都不得绕过服务端风控、操作确认或审计。
- LIVE 配置、账户停用/恢复、交易限制、清仓、权限授予等敏感操作应拆分独立权限；不得因用户拥有普通后台访问权而自动授予。

#### 会话、敏感操作与审计

- 登录成功后由服务端返回最小必要的身份/权限信息或提供当前会话查询接口。权限信息仅供界面展示；API 每次请求仍需使用当前有效身份重新授权。角色或账户 Scope 变更后，应及时使旧会话/令牌失效或确保后续请求立即采用新权限。
- 明确访问凭证的存储、有效期、续期、撤销、登出和失效处理。不得把 Token 放入 URL、日志或页面回显。当前前端使用 `localStorage` 保存 Token；上线前应评估 XSS 下的窃取风险并形成批准的会话方案。若采用 Cookie 会话，须配置 CSRF 防护及 `Secure`、`HttpOnly`、适当 `SameSite` 属性；若继续使用请求头令牌方式，应控制其存储、传递、有效期、刷新和撤销，并明确令牌本身不提供防重放保证。
- 管理端退出会调用 `POST /api/v1/auth/logout` 撤销当前 Access Token，并无论请求结果如何都清除本地 Token；网络失败时明确提示“服务端撤销未确认”，不得宣称远端会话已注销。API 还支持客户端可选提交 Refresh Token，并仅在其主体与当前 Access Token 一致时撤销；当前 Web 客户端仅保存 Access Token，因此不发送该可选字段。
- 管理员账户应启用 MFA；密码重置、角色/Scope 授予、敏感配置变更及高风险风控操作应按威胁模型要求进行 MFA 或 step-up 重新验证。具体认证器、会话时限和重新验证策略须在部署前审批，不能由前端确认框代替。
- 登录及认证失败应应用分层限流、攻击检测和安全审计；可信代理 IP 仅用于经过验证的网络策略，不得代替身份和资源授权。防误封、过期恢复和告警策略按系统安全设计执行。
- 审计至少记录操作者主体、授权角色/Scope、动作、目标资源、时间、结果、拒绝原因分类和 trace ID；不得记录密码、Token、密钥或完整敏感请求。登录成功、失败、登出、会话撤销、授权变更和高风险操作均应有可检索记录。

#### 管理登录与权限验收

- 有效 `ROLE_TRADER`（或其他非管理角色）凭证访问管理页面和直接调用管理 API 均被拒绝；不能只验证 UI 菜单隐藏。
- 管理角色缺失、Scope 不匹配、目标资源不属于授权范围、用户停用、会话过期/撤销等场景均由后端拒绝，并分别返回合适状态；不得通过更换 URL、请求参数或直接构造 API 请求绕过。
- 前端覆盖未登录、无管理权限、权限状态加载失败、会话过期、Token 撤销和重新登录状态；无权与服务不可用不能显示成空数据或成功。
- 验证角色/Scope 变更生效时间、MFA/step-up 策略、认证限流和相关审计记录；全部使用 mock/test 环境，不使用真实账户或生产身份。

### 3.2 用户管理

**页面能力**

- 用户列表：分页、按用户名/启用状态/角色过滤；显示用户状态、当前绑定账户及更新时间等必要字段。
- 新建用户：输入最小必要信息；密码只提交不回显；账户关联作为单独明确步骤或事务化流程。
- 用户详情/编辑：修改允许字段、展示当前状态和绑定概况；禁止修改只读审计字段。
- 启用/停用：说明停用对登录、Token 和账户操作的影响；确认后执行并展示结果。
- 密码重置：独立操作、强校验、完成后不得返回密码；审计操作者和目标用户。

**业务规则**

- 用户名唯一；停用用户不可继续认证或访问受保护 API。
- 创建用户与创建/绑定券商账户的事务边界要明确，部分失败时不产生难以恢复的孤儿数据。
- 用户删除优先采用停用/软删除策略，保留其订单、成交和审计关联。

### 3.3 券商账户与绑定管理

- 账户列表/详情展示所属用户、券商、账户号（遵循最小暴露，可遮罩）、账户类型、LIVE/SANDBOX 环境、状态、开发者账号引用和当前绑定状态。
- 新建/编辑校验用户、券商、券商开发者账号、账户号唯一性、账户类型、环境和状态。
- 账户关闭采用停用语义，不硬删除关联交易历史。
- 用户绑定/切换显示当前绑定与目标账户，校验目标账户 ACTIVE、未被其他用户占用，并对“解绑旧账户+绑定新账户”使用事务。
- 绑定成功后使缓存/会话中的旧账户上下文失效；下次交易须由服务端重新解析绑定和环境。
- 明确用户可拥有多个账户但仅一个“当前账户”，或采取其他产品规则；此规则必须和 DB 约束、API、页面一致。

### 3.4 在仓监控、订单与风控

- 在仓监控按用户/券商账户分组展示持仓数量、均价、现价、市值、未实现盈亏和数据时间；支持分页/筛选。
- 订单管理按状态、用户、账户、标的、时间范围筛选；订单“管理标记”不能伪装成券商侧真实订单状态。
- 取消订单前确认订单仍可取消，并以券商返回结果为最终状态；请求超时应提示查询状态，不能自动重复写操作。
- 风控页面（如纳入首发）展示状态、触发来源、操作者、时间和备注；disable/enable/limit 必须说明影响范围。
- 强制清仓采用多步骤确认，显示目标账户、环境、受影响持仓和异步执行状态；操作记录必须可追溯，不显示“已完成”除非后端确认。

### 3.5 审计、公司与券商配置

- 审计页按时间、操作者、目标用户/账户、动作、结果筛选，采用服务端分页；提供详情但脱敏凭证、请求敏感字段和完整账户标识。
- 公司/租户页面维护名称、状态及组关系；对多租户可见范围必须由后端 Scope 过滤，不依赖前端过滤。
- 券商配置页面只开放允许的模式和端点参数；环境切换展示清楚并要求确认。密钥只以安全引用方式配置，永不读取/回显明文。
- 全局配置和账户级 `api_environment` 的优先级要唯一、明确；禁止通过 UI 配置把测试账户指向生产端点或绕开风险控制。
- 列表页面提供加载、空结果、失败重试、无权限和过期状态；所有写操作显示明确成功/失败，不吞掉错误。

### 3.6 API 校验与错误响应契约（已确认目标）

**现状**：后端 `dto.common.ApiResponse`、`dto.ApiResponse`、Spring Security 与 FIX Gateway 错误出口，以及 Flutter Dio、Web Axios 响应解析，已按 V1 `code/message/data` 契约迁移。错误 `data` 固定包含 `fieldErrors` 和 `traceId`；完整 API 回归及已部署调用方升级仍待验收。

**已确认目标（2026-11-20）**：统一使用 `code/message/data`；`code` 为稳定业务码，HTTP 状态码独立表达；错误时 `data` 使用结构化载荷。

成功响应示例：

```json
{
  "code": "SUCCESS",
  "message": "请求处理成功",
  "data": {
    "id": 123
  }
}
```

校验错误示例：

```http
HTTP/1.1 400 Bad Request
```

```json
{
  "code": "VALIDATION_ERROR",
  "message": "请求参数校验失败",
  "data": {
    "fieldErrors": [
      {
        "field": "email",
        "code": "INVALID_FORMAT",
        "message": "请输入有效的邮箱地址"
      }
    ],
    "traceId": "01J..."
  }
}
```

- 所有成功与错误响应均使用相同外层字段。成功时 `data` 是接口结果；错误时 `data` 包含 `fieldErrors`（无字段错误时为空数组）和服务端生成/验证的 `traceId`。不得信任未验证的客户端 trace ID。
- `code` 来自统一业务码注册表；成功码为 `SUCCESS`，错误码一经发布即为稳定 API 契约。客户端只能按 `code`/HTTP 状态分支，不得依赖 `message` 文案。
- `fieldErrors[]` 的 `field` 使用请求 DTO 属性路径，`code` 是稳定机器码，`message` 是安全可读说明；同字段多项错误按确定顺序返回。
- HTTP 状态通过 4xx/5xx 表达通用协议语义；下表为首发建议映射，阶段 1 通过契约测试冻结。认证失败不得泄露账号是否存在；交易结果未知时先查询状态，不自动重放写请求。
- 错误响应不得包含 `rejectedValue`、密码、Token、完整请求体、堆栈、SQL 或券商原始响应。未知异常只向客户端返回通用消息；日志仅记录脱敏诊断信息。

| HTTP 状态 | 冻结业务码 | 使用场景 |
|---|---|---|
| 400 | `VALIDATION_ERROR`、`INVALID_ARGUMENT`、`INVALID_STATE`、`STOCK_NOT_FOUND`、`STOCK_NOT_WHITELISTED` | 参数/字段校验失败或当前状态不允许操作 |
| 401 | `UNAUTHORIZED`、`INVALID_CREDENTIALS`、`TOKEN_EXPIRED`、`TOKEN_INVALID`、`REFRESH_TOKEN_EXPIRED` | 未认证或会话失效 |
| 403 | `ACCESS_DENIED`、`ACCOUNT_RISK_BLOCKED` | 身份有效，但角色、Scope、资源授权或风控状态拒绝操作 |
| 404 | `RESOURCE_NOT_FOUND`、`NOT_FOUND`、`ACCOUNT_NOT_FOUND` | 资源不存在；敏感资源按威胁模型避免泄露其存在性 |
| 409 | `ORDER_RESULT_UNCONFIRMED` | 订单提交结果尚未确认；先查询状态，不自动重放 |
| 429 | `TOO_MANY_REQUESTS` | 触发限流；适用时附 `Retry-After` |
| 503 | `BROKER_UNAVAILABLE` | 券商依赖不可用；交易结果未知时不得盲目重试 |
| 500 | `INTERNAL_ERROR` | 未预期服务端错误，客户端显示通用消息并展示可用的 `traceId` |

**管理端处理规则**：`request.ts` 保留 HTTP 状态及响应体 `code/message/data`；401 按安全规则清理本地会话并跳转登录，403 显示无权状态而不循环跳转。表单按 `data.fieldErrors[].field` 回填；非表单错误展示安全的 `message` 和可复制的 `data.traceId`。网络错误、超时、限流、依赖故障和结果未知分别呈现；不得将失败伪装成成功或自动重试交易写请求。

**实施与发布门**：后端两种 `ApiResponse`、Security/FIX 错误出口与 Flutter/Web 解析已迁移，并有契约序列化、认证响应及 trace ID 定向验证；完整 API 回归尚待完成。Flutter/Web 仍可解析旧版成功包装以支持协调发布期间的存量服务，但后端不再输出旧别名。发布新后端前须确认所有已部署客户端及获授权调用方已升级；独立外部 API 客户端不纳入首发，阶段 8 评估时另做兼容审查。

### 5.2 数据权威来源与持久化边界

券商 API 能返回数据，不代表本系统应复制并长期保存全部响应。按数据的权威来源和本系统的业务责任分别处理：

| 数据域 | 权威来源 | 本系统持久化策略 | 目的与边界 |
|---|---|---|---|
| 用户、角色、Scope、账户绑定和账户权限 | 本系统 | **必须保存** | 作为登录、授权和账户归属依据；不能每次依赖券商 API 判断 |
| 本地订单意图与提交状态 | 本系统 | **必须保存** | 记录操作者、账户、标的、方向、数量、订单类型、提交时间及本地生命周期，支持幂等、查单、审计和故障恢复 |
| 券商订单标识、订单状态变化和成交 | 券商为成交/执行事实来源；本系统为操作记录来源 | **保存必要字段/事件** | 关联本地订单与券商订单，支持状态追踪和对账；不要求镜像完整券商响应 |
| 当前余额、购买力、当前持仓 | 券商或被确认的账户数据源 | **优先实时读取；按需缓存或保存精简快照** | 若为性能、离线展示、历史分析或对账保存快照，必须包含来源、采集时间和适用账户；过期状态不能伪装成实时 |
| 当前行情 | 行情提供方/Mock | **优先实时读取或短期缓存** | 只在确有历史行情、回测或审计需求时另行定义行情历史存储；缓存需有 TTL 和来源/时间语义 |
| 券商完整原始响应、全量行情历史 | 外部提供方 | **默认不持久化** | 避免重复镜像、无界增长及敏感数据扩散；确有业务需求时，单独定义字段白名单、用途、访问权限和保留期限 |
| 密码、访问/刷新 Token、券商密钥 | 认证/密钥设施 | **不得明文持久化或记录日志** | 密码只存哈希；凭证使用受保护的密钥存储或 Secret 引用，不进入普通业务表、前端或审计详情 |

订单必须先形成本系统可追踪的提交记录，再调用交易提供方，并明确状态流，例如 `SUBMITTING`、`UNKNOWN`、`ACCEPTED`、`REJECTED`、`FILLED`、`CANCELLED`。如果请求超时或响应丢失，券商可能已接收订单；此时保留 `UNKNOWN` 及关联信息，通过查单/对账确定结果，**不得因本地暂时查不到订单就盲目重复提交**。

幂等键应绑定用户/主体、账户和请求内容，并具备跨进程、服务重启及缓存过期后的持久约束或可恢复记录。Redis 可用于短期并发协调，但不能作为唯一幂等账本，也不能用有 TTL 的键代替订单持久化和结果核验。

### 5.3 数据保留期限与定期清理

所有持久化数据都必须有明确的保留/删除策略。不得以“数据库容量足够”或“券商还能查到”为由无限期保存；也不得在保留期限、合规要求未确认时自行删除交易与审计证据。

| 数据类别 | 保留期限基线 | 到期处理 | 待确认事项 |
|---|---|---|---|
| 用户账户与授权关系 | 账户有效期间保留；停用/注销后按安全、争议处理及法规要求确定期限 | 先撤销会话、权限和凭证；到期后删除或匿名化非必要个人信息 | 停用是否立即撤销 Token；注销后的法定保留期限 |
| 本地订单、成交及订单状态事件 | 按适用金融法规、合同和争议处理要求确定；订单生命周期未终结或结果为 `UNKNOWN` 时不得清理 | 到期后按依赖顺序归档/删除；可依法匿名化身份字段，但保留必要交易证据 | 适用司法辖区、记录年限及归档要求 |
| 操作、登录、API、安全审计日志 | 按安全调查、审计和法规要求设置分类期限；不得无限期保留 | 定期清理已过期且无保留标记的记录；删除前确保审计查询和调查窗口已满足 | 各日志种类的期限和审计要求 |
| 余额/持仓/行情快照与短期缓存 | 缓存按 TTL；快照按具体产品用途设置期限 | TTL 自动过期；数据库快照由清理任务按采集时间分批删除/归档 | 是否需要历史报表、对账或离线展示及相应期限 |
| 幂等/请求协调记录 | 至少覆盖订单结果不确定的解决周期；不得仅用短 TTL 导致可重复下单 | 订单终态及对账完成后，按重试/争议窗口清理辅助记录；关键幂等关联可随订单记录保留 | 最大重试窗口和争议处理周期 |
| 凭证、临时文件和诊断数据 | 凭证有效期内使用；诊断数据设最短必要期限 | 凭证撤销后销毁或轮换；临时文件和到期诊断数据自动删除 | Secret 设施能力、诊断用途及期限 |
| 备份及归档 | 按灾难恢复和法规要求设置独立期限 | 按备份轮换计划淘汰；主库删除不代表备份立即消失，需定义备份中的到期清除周期 | RPO/RTO、备份保留周期及法律保留要求 |

上表中的具体天数/年限属于产品、法务/合规和运维决策，必须在上线前逐类填写并获批准；未确认的类别不得上线长期采集或默认无限保留。业务时钟应明确从何时起算（例如事件发生、账户注销或快照采集时间），并统一使用 UTC 时间存储/比较。

**定期清理任务要求**

- 使用后端受控的计划任务/维护作业执行清理，频率和批量大小可配置；任务须幂等、可重入、可暂停，并避免长事务和高峰期的大批量锁表。
- 仅按“数据类别 + 到期时间 + 无法律保留/调查冻结标记”筛选；订单仍未终结、状态为 `UNKNOWN`、存在未完成对账或争议冻结的数据不得删除。
- 对有外键/审计关联的数据按依赖顺序处理；优先归档或匿名化经批准的个人字段，不得破坏订单、成交和审计的必要关联。
- 清理操作生成最小化的执行摘要（任务、时间范围、类别、条数、结果/失败数），不能在清理日志中复制敏感数据，也不能记录被删除记录的秘密值。
- 监控上次成功时间、待清理量、处理条数和失败；失败必须告警且可安全重试，禁止静默跳过。
- 明确备份、只读副本、缓存及导出文件的独立保留/删除机制；向用户或运维说明“主库已删除”和“备份轮换后彻底过期”的差别。
- 测试环境验证到期边界、法律保留、任务重跑、部分失败、关联完整性和大批次行为；生产数据清理需有授权、审计及必要的恢复方案。

### 5.4 数据关系与一致性要求

- `users.current_broker_account_id` 指向 `t_broker_account.id`；V18 已添加外键，但“一个券商账户最多被一个用户当前绑定”的唯一性还需数据库/事务设计保障。
- `t_broker_account` 关联用户、券商和可选开发者账号；券商账户号按 `(broker_id, account_no)` 唯一。
- `t_broker_account_permission` 对同一账户的权限应唯一；业务操作须检查权限表，而不只看页面开关。
- `t_group` 依赖公司；Scope 记录管理员与目标用户/账户范围。需核查目标账户 ID 类型以及撤销/失效语义。
- 风控状态应以稳定的账户内部标识关联账户主数据，避免仅以可变或格式不统一的券商账户字符串关联。
- `t_broker_runtime_config` 是全局配置，`t_broker_account.api_environment` 是账户级环境；确定优先级与禁止组合，避免 LIVE/SANDBOX 混用。
- 订单、持仓、成交和审计历史应保留业务关联；用户停用/账户关闭不应级联删除交易证据。

### 5.5 数据安全、迁移与查询要求

- 只以新的 Flyway 版本迁移结构；V1～V26 等已应用 migration 不得修改。先读取目标环境迁移版本及实际列、索引、外键。
- 对 `app_key`、`app_secret`、Broker Token 和其他凭证采用外部密钥管理、加密存储或仅保存 Secret 引用；列表/详情 API 从不返回秘密值。
- 订单幂等和不确定结果处理不能只依靠 Redis TTL；若需新增订单状态、请求摘要、事件或对账字段，应先检查当前 `orders`/成交表和已应用 migration，再设计向前兼容的新 migration。
- 余额、持仓、行情快照仅在产品明确需要时新增；每类快照必须定义采样频率、来源、时间戳、过期语义、保留/归档和查询用途。
- 不保存不必要的完整券商请求/响应；用于排障的有限诊断信息须字段白名单化、脱敏并设定短保留期限。
- 统一 V11 与 V19 两套日志表的权威来源；迁移或切换前确认数据保留、查询兼容和审计完整性。
- 对用户列表、账户列表、持仓、订单、日志和事件查询实施服务端分页、时间范围和索引；不允许无界全表扫描式管理接口。
- 重要管理写操作保存操作者、动作、目标、时间、结果及必要的前后值摘要；敏感字段在存储和查询前脱敏。
- 实施上述分类型保留策略和定期清理作业；操作日志不能由被审计的普通管理员任意修改或删除，清理本身也必须受控并留有最小化执行审计。
- 新增唯一约束/外键前先检查历史重复/孤儿数据，并提供测试环境数据修复和生产升级方案。

### 5.6 系统级日志、监控与告警设计

系统日志的目标是让开发和运维人员能按一次请求、一个订单或一个后台任务还原关键时间线，并在影响扩大前及时发现问题。日志、审计记录和监控指标各有用途，不能互相替代；不要求把所有运行日志写入业务数据库。

**日志分类与去向**

| 类别 | 记录内容 | 主要用途 | 建议去向 |
|---|---|---|---|
| 应用运行日志 | 启动/关闭、依赖状态、异常堆栈、配置校验失败、作业开始/结束 | 定位服务故障 | 结构化应用日志输出；由部署环境采集、集中检索并按期限轮转 |
| API 请求/访问日志 | trace/request ID、路由模板、HTTP 方法/状态码、耗时、结果类别、调用方主体 ID（必要时） | 关联慢请求、错误率和权限问题 | 日志平台；API 调用审计表只保留管理查询确需的字段 |
| 安全与管理审计 | 登录成功/失败、授权拒绝、用户/账户/权限/配置变更、危险操作确认、操作者/目标/结果 | 追责、合规和安全调查 | 受访问控制的持久审计存储；不允许普通管理员修改或清除 |
| 交易业务事件 | 本地订单状态转换、幂等命中/冲突、取消结果、`UNKNOWN` 结果、对账差异 | 还原交易闭环和故障时间线 | 业务事件/订单状态记录；与普通运行日志通过 trace ID、订单内部 ID 关联 |
| 监控指标 | 请求量/错误率/延迟、JVM/进程、线程池、DB/Redis 连接池、作业积压、清理任务结果 | 趋势、容量和告警判断 | 指标监控系统；避免把高基数用户/账户标识作为指标标签 |

**统一字段与关联**

- 使用结构化 JSON 或项目选定的等效结构化格式；时间统一 UTC，并包含服务名、环境、版本、日志级别、事件名和可用的 `traceId`/`requestId`。
- API 入口生成或校验 trace ID，并在服务调用、数据库操作摘要、后台任务和响应头间传递；拒绝不符合长度/字符约束的外部 trace 值，避免日志注入。
- 对订单事件使用内部订单 ID、幂等请求标识的安全摘要和必要的券商订单 ID 进行关联；日志不得把完整幂等密钥当普通文本输出。
- 错误日志保留异常类型、错误码、堆栈和必要上下文；客户端响应使用稳定错误码和 trace ID，不返回内部堆栈、SQL 或凭证。

**必须覆盖的调查点**

- 认证/授权：登录失败与限流、Token 失效、权限拒绝、账户归属拒绝；记录主体（若可识别）、目标资源类型/内部 ID、结果和 trace ID，不记录密码/Token。
- 交易：提交前校验结果、幂等检查结果、请求进入/退出券商 Adapter 的阶段、耗时、返回分类、本地订单状态转换、撤单、超时未知态与对账差异。当前阶段只允许 Mock；真实 Adapter 或外部交易 API 调用尝试应被配置拦截并触发高优先级告警，不得自动回退。
- 管理写操作：谁在何时对什么对象执行了何种变更、授权判断、结果/失败码及必要的前后值摘要；秘密字段不写入摘要。
- 后台作业：作业名、运行 ID、开始/结束时间、处理/跳过/失败数量、游标或时间窗口摘要、耗时和重试结果；不输出被处理记录的敏感内容。
- 数据库/依赖：连接失败、迁移失败、连接池耗尽、查询超时、Redis 不可用及服务健康状态；避免记录含敏感值的完整 SQL 参数。

**告警分级与通知**

| 等级 | 例子 | 处理目标 |
|---|---|---|
| Critical | 未授权外部 API/真实券商调用尝试、可能导致重复/错误订单的状态异常、关键数据库不可用、疑似凭证泄漏 | 立即通知值班责任人并升级；隔离相关写操作，保留调查证据 |
| High | `UNKNOWN` 订单持续无法核实、管理写操作持续失败、认证/权限异常突增、清理任务连续失败或审计写入中断 | 尽快人工调查；必要时关闭受影响功能 |
| Medium | API 错误率/延迟持续超过批准阈值、依赖间歇性故障、磁盘/连接池/待处理任务接近容量上限 | 在约定处理时限内排查并跟踪趋势 |
| Low/Info | 单次可恢复异常、常规作业摘要、容量趋势提示 | 记录、聚合和定期复核，避免打扰值班 |

- 阈值、持续窗口、通知对象、值班时段和升级时限由运维在容量基线和业务风险评审后配置；不在缺乏依据时把示例描述当作固定 SLA。
- 告警规则需做去重/抑制、恢复通知和关联 trace 查询链接；同一故障不能因每条日志都生成通知而造成告警风暴。
- 关键交易安全和数据丢失类规则不能只依赖日志字符串匹配；应结合订单状态/审计事件及错误率、延迟、健康状态等指标。
- 当前开发/验收阶段不连接外部券商、交易 API 或外部通知服务。先用本地监控、控制台/测试告警接收器验证规则；邮件、短信、IM、Pager 等通知渠道须经用户/运维另行批准后再接入。
- 告警通知只包含级别、服务、错误类别、时间和 trace ID 等最小信息；不包含 Token、券商密钥、账户凭证、完整订单请求或不必要的个人信息。

**敏感信息与运行要求**

- 禁止记录密码、Authorization/Cookie、JWT/Refresh Token、券商密钥、Secret、完整账户凭证、支付/身份信息；对账户号、用户标识、订单字段按用途脱敏或使用内部 ID。
- 日志内容不得直接拼接不可信换行符；异常和外部错误文本需清理控制字符并限制长度。
- 运行日志按前述保留策略轮转/清理；审计及订单事件依独立合规期限保留。定义采集器不可用、磁盘满、审计存储不可写时的降级与告警策略，不得静默丢弃关键审计。
- 访问日志平台和审计查询均采用最小权限、分页、查询审计和数据导出控制；所有日志/指标标签避免高基数数据和秘密内容。

### 5.7 网络攻击防护与自动 IP 限制

目标是在攻击流量影响交易和管理功能前进行检测、限速、临时隔离和告警，同时避免误封正常用户或把自动化控制变成新的拒绝服务风险。IP 阻断是纵深防御的一层，不替代认证、授权、应用安全和上游 DDoS 防护。

**入口与网络边界**

- 对公网入口使用 TLS；根据部署环境配置网络防火墙、WAF 和上游 DDoS 防护。大流量/链路饱和攻击必须依靠网络/CDN/云服务商的清洗能力，应用层 IP 封禁无法单独解决。
- API 和 Web 管理端按需开放；MySQL、Redis、内部管理接口和运维端口只允许受控网络访问，不直接暴露公网。生产、测试和开发网络/凭证隔离。
- 管理端可按部署风险配置 VPN 或来源 CIDR 允许名单，并保留受控的紧急恢复途径；允许名单只缩小网络入口，不能绕过 MFA、身份认证和服务端授权。来源范围须最小化并定期复核。
- 客户端 IP 只能从明确配置的可信代理链解析。边缘代理移除公网来访者自行提供的转发头；应用不得盲目信任任意 `X-Forwarded-For`/`Forwarded`。覆盖 IPv4、IPv6、负载均衡和应用多实例。

**系统级与公司级 IP 策略**

- IP 控制同时有系统级和公司级，职责不可互相替代。服务器/云防火墙/WAF 在入口做粗粒度网络准入、恶意流量拦截和 DDoS 缓解；应用系统基于可信来源 IP、认证主体、路由和风险信号执行统一限流、动态攻击判定、审计和临时阻断。应用自动检测结果可通过受控流程同步到 WAF/网关，但不得由应用直接改写服务器防火墙规则。
- **系统级安全设置页**统一管理全局临时/人工封禁、管理员控制台的受信来源策略、默认限流/阻断策略、封禁到期与解除、可信代理配置和处置审计。全局封禁优先级最高；管理员来源允许名单不能豁免全局封禁，也不能替代管理员身份认证/MFA。
- **公司详情页的“安全与 IP 访问”设置**供获授权的平台管理员配置该公司办公/开发出口 CIDR 白名单，可启用/停用并查看生效范围、最近修改人和时间。启用后只允许该公司已归属的普通用户会话以及明确绑定到该公司的 API/MCP 客户端从名单来源访问；不支持公司 Scope 的身份不得仅凭请求参数选择公司来套用白名单。
- 公司级白名单是附加限制，不是信任名单：启用时须同时通过全局规则、公司 CIDR 规则、认证、用户/客户端授权和资源归属检查。公司白名单不能解除系统全局封禁、覆盖账户权限/限流或让该公司访问其他租户资源。公司未启用白名单时仍受所有系统级规则约束。
- 策略判定顺序：可信边缘解析真实客户端 IP → 系统全局封禁/紧急阻断 → 系统级路由和身份限流 → 根据已认证身份解析唯一公司 Scope → 若该公司启用白名单则校验 CIDR → 常规认证授权、账户归属和业务风控。任何拒绝都记录规则 ID/作用范围/原因和 trace ID，但不得记录凭证。
- 租户白名单变更属于安全敏感管理操作：需平台管理员授权、二次确认（如风险要求）、完整审计并立即作用于后续请求；修改错误时需支持受控恢复路径。禁止普通公司用户自行添加任意 IP、扩大 CIDR 或修改系统级规则。
- 公司白名单和临时封禁须存为规范化 IPv4/IPv6 CIDR/地址策略，而不是只存单个 IPv4 字符串；清晰限制条目数量与 CIDR 范围，防止 `0.0.0.0/0`、`::/0` 等过宽规则造成误配置。系统自动封禁始终有 TTL；公司 allowlist 永久启用也须定期复核。
- 页面职责：系统级封禁与平台管理员来源限制放在系统安全设置/安全事件页面；各公司办公/开发来源白名单放在公司详情的“安全与 IP 访问”页签。MVP 暂无公司管理员自助管理时，由平台管理员代为维护并审计，不新增无依据的角色授权。

**检测、限速与自动阻断**

- 按路由风险分级设置限流：登录/密码重置、管理写操作、交易写操作和昂贵查询分别控制；组合来源 IP、账号/认证主体、路由和全局容量信号，避免仅按单一 IP 限制而误伤共享 NAT 用户。
- 对认证失败突增、明确的自动化扫描/攻击模式、异常请求速率及多次越权尝试进行关联检测。单次普通校验错误或单个 4xx 不应直接永久封禁；检测规则、阈值和持续窗口由安全评审与基线测试确定。
- 采取分级响应：先限速/短暂冷却；达到配置的高置信阈值时，对来源 IP 或必要的 IP+路由组合立即施加有 TTL 的临时阻断并触发告警；持续/重复事件可按批准规则延长并升级人工处置。自动策略默认不创建永久封禁。
- 封禁状态须能跨实例一致生效，记录规则/触发原因、起止时间、范围、置信依据和处置来源；支持 TTL 到期自动解除、授权人员人工解除/延长、审计与告警。人工配置的永久网络策略必须与自动临时封禁分开管理。
- 受信运维/健康检查流量使用明确且最小化的来源规则；提供有审计的紧急恢复路径，防止错误规则或自动封禁锁死所有管理员。不得对整个云厂商/运营商网段做宽泛封禁。
- 限流/封禁计数不可用时不得静默关闭保护：按风险定义降级（例如边缘层继续执行、管理/认证/交易写操作采用保守限制），产生告警并保留健康访问能力；不得让计数故障引发无界请求。

**其他必要防护**

- 登录保护同时按账号和来源进行渐进延迟/短时锁定，结合 MFA、强密码策略、密码哈希、会话失效/撤销与登录告警；错误响应不泄露账号是否存在。验证码或交互挑战只能作为额外控制。
- 服务端对每个端点执行认证、角色/Scope、账户归属和资源级授权；管理写操作采用最小权限、必要时重新认证，并保留不可由普通管理员篡改的审计。
- API 输入使用类型、长度、范围和格式白名单校验；数据库查询参数化，输出上下文编码；按场景防护 CSRF、CORS 滥用、XSS、SQL/命令注入、SSRF、路径穿越、反序列化及文件上传滥用，并设置请求体/文件/查询成本上限。
- 部署安全响应头、严格 CORS 来源、Cookie 属性和会话策略；禁止把秘密放在 URL、前端代码、日志或错误响应中。密钥集中管理、最小授权、定期轮换并支持泄漏后的快速撤销。
- 对依赖、容器/构建产物和 CI/CD 权限开展持续漏洞检查；限制发布凭证与工作流权限，保护依赖来源和构建产物。备份与生产凭证隔离、限制访问并定期验证恢复。
- 建立事件响应步骤：确认告警与影响面、限制来源或暂停相关写操作、撤销泄漏会话/密钥、隔离受影响组件、保全审计证据、恢复服务并复盘。关键处置动作需授权、记录和事后检查。

**验收与待决配置**

- 安全测试覆盖：外部伪造转发头不能伪造来源 IP；可信代理链解析正确；IPv4/IPv6 一致；跨实例限流/阻断生效；系统级封禁优先于公司白名单；公司 A 的白名单不影响公司 B 且不能跨租户选择 Scope；公司白名单开启/关闭和 CIDR 更新即时生效并有审计；封禁按期到期并可审计解除；共享出口不会仅因他人异常被无限期封锁；紧急恢复路径有效；计数后端故障触发预期降级和告警。
- 安全阈值、封禁时长、升级对象、允许名单负责人、管理端是否强制 VPN/MFA、通知渠道与响应 SLA 均属待批准配置，不在设计阶段臆定固定数值。当前开发验收只在本地/隔离环境使用模拟来源和测试接收器，不连接外部交易 API、真实券商或外部通知服务。

## 6. 优先实施顺序与交付物

### 阶段 A：现状和契约核对

- 交付：页面/API/权限矩阵、差异清单、管理端首发范围及 DB 现状清单。

### 阶段 B：管理端功能与数据设计

- 冻结管理员角色和 Scope；确认用户、公司、组、账户绑定及风控工作流。
- 冻结页面状态、筛选字段、分页、危险操作确认和审计内容。
- 冻结 DB 权威数据源、表关系、唯一约束、索引、凭证处理、各类数据保留期限、定期清理/归档策略和迁移方案。
- 冻结日志分类/字段/脱敏规则、关键事件清单、告警分级和接收流程；具体阈值根据运行基线确认。
- 冻结网络边界、可信代理链、系统级与公司级 IP 策略边界/优先级、按风险分层的限流与临时 IP 阻断规则、页面和 API 权限及攻击响应责任人。
- 交付：页面功能规格、API 契约补充、ER/字段映射及 migration 设计。

### 阶段 C：实现和联调

- 先统一认证、路由/API 前缀、响应/错误处理和服务端权限。
- 补齐用户/账户/绑定管理和审计核心流程，再接入订单/风控/配置高风险能力。
- 新 DB 变化以版本化 migration 实施；前端错误、空状态和权限状态完整处理。
- 实现结构化日志、trace ID 贯通、核心运行/交易事件和基础健康/错误/延迟指标；在本地或测试告警接收器验证告警及恢复通知。
- 实现并验证可信来源解析、关键路由限流、系统级临时 IP 阻断/解除、公司详情的办公/开发 CIDR 白名单、登录保护和管理端网络边界；不新增安全配置表前须先核验现有配置及部署能力。
- 交付：可运行的管理端页面、管理 API、migration、审计及操作说明。

### 阶段 D：验收

- 使用 mock/test 账户验证管理员登录、用户创建/停用、账户创建/绑定/切换、持仓/订单查询、审计检索、到期数据清理任务及模拟告警。
- 测试非管理员访问、直接调用管理 API、Scope 越权、角色变更、停用用户、会话过期/撤销、认证限流及权限审计；另测试重复提交、LIVE 配置保护、券商超时和异步清仓失败等场景。
- 测试 IP 伪造头、可信代理、IPv4/IPv6、多实例限流、全局封禁优先级、公司间白名单隔离、临时封禁到期/解除、误封恢复及攻击告警。
- 执行管理端 `npm run build`，并运行 API 模块相关测试/`mvn test`；真实账户与生产操作不在验收中。
- 交付：测试证据、遗留问题和延期项、管理员使用手册。

## 7. 完成标准

- 每个首发管理页面都有确定路由、功能、API、权限、数据来源和测试用例。
- 服务端强制执行管理员角色及目标范围；前端守卫不作为唯一安全控制。
- 用户、券商账户、绑定、风控和配置变更均可审计；凭证不回显或明文暴露。
- 关键请求可通过 trace ID 贯通 API、服务、订单/作业事件；关键失败可触发去重告警并能发送恢复通知。
- 关键入口有经验证的限流和攻击响应；自动 IP 限制可解释、可过期、可审计且不会绕过授权或造成不可恢复的管理员锁定。
- 管理列表分页且可检索；错误、空状态、超时和无权限均有可理解反馈。
- 数据库升级只新增 migration，并通过测试环境空库安装及既有库升级验证。
- 风控页面/业绩页面等未实现能力明确标为已实现、延期或不纳入 V1，不留误导性入口。
- `npm run build` 与 API 相关验证有实际执行记录；未执行项不得标记为通过。

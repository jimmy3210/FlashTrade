# 18-MCP 接入设计

## 1. 目标与定位

MCP（Model Context Protocol）是 QuickTrade 面向 AI 客户端的受控工具接入层，用于让获授权的 AI 客户端以标准化方式调用 QuickTrade 的行情、账户、持仓和订单能力。

MCP 不替代 QuickTrade API，不直接连接券商，也不另建一套交易后台。自有 UI、其他 API 客户端和 MCP Server 最终都复用 QuickTrade API 与同一套后台业务服务；认证、授权、限流、风控和审计规则不能因调用方是 AI 而被绕过。

```text
QuickTrade UI ────────────────┐
其他 API 客户端 ──────────────┼──→ QuickTrade API
MCP Host / AI Client → MCP Server ┘       ↓
                                  认证 / 授权 / 限流
                                           ↓
                                  业务服务 / 风控 / 审计
                                           ↓
                                    Broker Adapter
                                           ↓
                                      Broker API
```

MCP Server 负责将经过审核的工具映射到 QuickTrade API，执行工具级输入校验并传递已验证的调用者身份。它不是任意 API 代理，不能直接访问数据库、券商凭证或 Broker API。

## 2. 设计原则

- **复用业务能力**：MCP 工具调用 QuickTrade 统一 API，不复制订单、账户或风控业务逻辑。
- **最小权限**：只暴露明确、有限、可审计的工具；按用户、客户端、账户和工具分别授权。
- **只读优先**：第一阶段仅提供查询能力；交易写操作必须经过额外授权与确认流程后才能启用。
- **不信任模型输入**：模型提供的账户 ID、权限声明或“用户已确认”等文字不得作为身份、授权或确认凭证。
- **安全隔离**：不同 MCP 客户端使用独立身份和凭证；凭证支持撤销、轮换，不进入模型上下文或普通日志。
- **可追踪**：MCP 请求与后台 API 请求使用关联 ID，能够审计调用主体、工具、账户、结果及交易确认记录。
- **安全优先**：MCP 新能力不得弱化网络攻击防护、统一限流、账户隔离、密钥保护或事件响应要求。
- **最小化数据**：MCP 只返回当前授权任务所需的数据；不得因模型调用而复制或长期保存后台已经权威管理的数据。
- **交互一致**：任何 MCP 确认页或宿主 UI 都应遵循产品的可访问性、状态反馈和设计系统；高风险交易确认必须清楚展示完整参数，不能仅靠主题颜色、图标或模型文本表达风险。
- **安全边界不下沉**：UI、BFF、SSR、MCP Server 都是调用/展示层，不是业务授权边界。后台 API 必须逐请求验证身份、角色、Scope、资源归属、输入、风险与审计；不得因请求来自自有前端、服务内网或 MCP Server 而隐式放权。
- **最小响应与缓存隔离**：工具和服务端渲染层仅传递当前主体有权读取且任务必需的数据；不得将内部密钥、无关账户数据或未授权字段暴露给宿主/模型。用户相关响应需禁用共享缓存或按身份及 Scope 隔离。

## 3. 工具范围

工具应围绕清晰的业务动作设计，采用稳定的输入和结构化输出。不得提供 `execute_sql`、任意 URL/API 转发或等价的通用执行工具。

### 3.1 第一阶段：只读工具

| 工具 | 用途 | 关键输入 | 权限 |
| --- | --- | --- | --- |
| `search_symbols` | 搜索美股标的 | 查询词、可选分页参数 | `quotes:read` |
| `get_quote` | 查询指定标的行情 | 标的代码 | `quotes:read` |
| `list_accounts` | 查询调用者获授权的账户 | 可选分页参数 | `account:read` |
| `get_account_summary` | 查询账户摘要 | 账户范围由服务端授权确定 | `account:read` |
| `list_positions` | 查询持仓 | 账户范围、可选分页参数 | `positions:read` |
| `list_orders` | 查询订单列表 | 账户范围、状态/时间筛选、分页参数 | `orders:read` |
| `get_order` | 查询订单详情 | 订单标识 | `orders:read` |

账户选择必须由服务端基于已验证身份和授权范围解析。即使接口允许传入账户标识，服务端也必须重新校验其归属和权限。行情与账户结果应尽可能包含数据时间、延迟/实时状态及来源等元信息，避免把过期数据误认为实时数据。

### 3.2 第二阶段：受控交易工具

只有在独立交易权限和确认机制落地后，才考虑开放以下工具：

- `create_order`：提交新订单
- `cancel_order`：撤销订单
- `replace_order`：修改订单

每个写工具仅接受明确的业务参数；服务端应验证标的、方向、数量、价格、订单类型、账户状态、权限及用户配置的交易限额。MCP 工具不得绕过与 UI/API 相同的业务校验和风控。

## 4. 身份认证与授权

- MCP 客户端必须通过受支持的认证流程建立身份，MCP Server 将该身份安全映射到 QuickTrade 用户或 API 客户端；不得使用所有调用者共用的高权限身份。
- 用户委托访问和服务到服务访问应使用适合其场景的独立凭证与授权范围。具体协议和传输方式在实现阶段按 MCP 客户端支持能力及部署环境确定。
- 建议将权限范围拆分为 `quotes:read`、`account:read`、`positions:read`、`orders:read`、`orders:write` 等能力；写权限默认关闭，并可按客户端、用户和账户单独授予或撤销。
- 每次工具调用都必须在 QuickTrade API/后台重新执行认证、权限、账户范围和业务状态校验。MCP Server 的校验是额外边界，不取代后台授权。
- 客户端密钥、访问令牌和券商凭证不得交给模型作为提示词或工具参数；敏感凭证不得写入普通日志。

## 5. 交易确认、幂等与审计

- 下单、撤单和改单应采用明确的用户确认流程。确认应由受信任的 UI 或 MCP Host 展示完整交易内容并收集，不能把模型生成的自然语言或工具参数中的布尔值视为确认。
- 确认凭证应绑定具体调用者、账户、操作类型和完整订单参数，并设置短有效期；任何参数变化都需要重新确认。确认验证由 QuickTrade 后台完成。
- 写操作应使用幂等键。请求超时或结果不确定时，应先查询后台/券商订单状态，再决定是否重试，不能盲目重复提交。
- 审计记录至少包含调用者/客户端、工具名、授权账户、关联 ID、参数摘要、确认记录、请求时间和结果；对令牌、密钥及不必要的敏感数据做脱敏或不记录。
- Broker 返回的文本、标的说明及其他外部内容都应作为不可信数据展示或传递，不得将其中包含的指令当作系统指令执行。

### 5.1 股票交易关键安全控制

以下控制针对交易写操作；必须由 QuickTrade 后端权威执行，MCP Server、模型提示词或宿主 UI 都不能代替。任一关键授权、风控、幂等或审计依赖不可用时，应拒绝新的交易写操作并返回可追踪的失败，不得降级为放行。

- **交易权限默认关闭**：查询与交易写权限分离；写权限按调用者、MCP 客户端、账户和操作类型分别授予，默认关闭、可撤销、可设有效期。每笔交易提交前重新验证当前权限、账户状态、凭证状态及授权范围，不把会话建立时的授权视为永久有效。
- **账户与订单绑定**：账户由服务端根据已验证主体解析并校验归属，不信任模型提供或从上下文推断的账户标识。订单确认及幂等记录绑定调用者、客户端、账户、操作类型和规范化后的完整订单参数；不可跨用户、客户端、账户或不同参数复用。
- **独立且可配置的交易风控**：服务端在提交前校验标的可交易状态、买卖方向、数量/价格精度、订单类型、有效期、账户购买力/可用资金、持仓及用户/账户限额、交易时段和适用的价格保护规则。阈值、允许的订单类型/标的和特殊交易限制由产品、风险及合规责任人批准配置；模型不得生成、覆盖或放宽风控参数。市场数据缺失、过期或可信度不足时，按风险策略拒绝依赖该数据的交易，而不能假定价格有效。
- **原子化检查与防竞态**：权限和风险检查须在服务端交易提交路径再次执行，并以事务、锁、版本校验或等效机制防止并发请求绕过余额/额度/持仓限制。执行边界及失败恢复需要与现有订单服务和 Adapter 设计一致。
- **重放与重复交易防护**：写请求使用服务端校验的高熵幂等标识、请求摘要和唯一约束；拒绝重放、过期确认和参数变化后的旧确认。网络超时、进程重启或 Broker 响应不明确时将结果标为 `UNKNOWN` 并先查单/对账；没有可靠结果前不得盲目重试或以新幂等键重新提交同一意图。
- **撤单、改单和部分成交安全**：撤单/改单须重新校验账户、订单所有权、当前状态及权限，并分别确认其具体目标和变更内容。撤单请求已受理不代表订单已取消；部分成交、状态竞争和 Broker 拒绝须准确反映。不得把重试撤单或改单当作无副作用操作。
- **紧急停止与故障关闭**：提供经授权、可审计的全局/账户/调用者级交易写入暂停能力，触发后立即阻止新的下单、改单及其他被策略定义的写操作，并告警。紧急停止不应被 MCP 自行解除；解除需重新授权并记录原因/审批。停止接单不等同于撤销已提交订单；是否批量撤单须作为独立、高风险且明确确认的操作，不得自动推断。
- **高风险变更保护**：交易权限开通、账户绑定/切换、限额放宽、Broker 凭证更新及紧急停止解除等管理变更，实施最小权限、强认证（如 MFA）和二次确认；是否要求双人审批应由风险评审明确。所有变更立即生效于后续请求，并可撤销。
- **凭证与会话保护**：Broker 凭证只由后端安全存储/密钥管理访问；MCP 工具不读取、传递或回显明文凭证。对凭证泄漏、用户停用、客户端撤销或权限变更提供快速撤销会话/令牌的流程。敏感凭证轮换不得写入日志、模型上下文或确认界面。
- **不可抵赖的交易审计**：对交易意图、参数摘要、权限/风控决策、确认凭证引用、幂等结果、提交阶段、Broker 结果分类和状态变化建立有访问控制、防篡改的审计链；审计写入失败时禁止新写操作。审计记录不保存不必要的完整凭证或秘密。
- **安全告警与事件响应**：对未授权写调用、反复风控绕过尝试、重复/异常订单、未知结果积压、紧急停止、凭证撤销和审计失败设置告警及升级流程。响应可撤销相关客户端权限、暂停交易写入、限制来源并保全证据；操作不得自动修改风控阈值以恢复交易。

## 6. 限流与运行控制

- MCP 请求同时受 QuickTrade API 的统一限流、周期配额和并发控制约束；可另为 MCP 客户端和工具设置更严格的限制。
- 按客户端、用户、账户和工具/操作成本分层计量。行情轮询、账户查询和交易写操作应分别设置策略，具体额度根据券商限制、系统容量和运行监控配置。
- 超限时沿用统一 API 的 `429 Too Many Requests` 语义及适用的 `Retry-After` 提示；MCP Server 不得通过重试风暴绕过限流。
- 记录 MCP 服务健康状况、工具调用成功率、延迟、拒绝原因和限流指标；对故障和凭证撤销提供可操作的告警与处置流程。

## 7. 安全、网络攻击防护与自动限制

- MCP Server 不得成为任意代理、开放转发器或绕过网络边界的入口。公网部署应采用 TLS、最小暴露端口及适用的 WAF/上游 DDoS 防护；数据库、Redis 和内部管理端点不得因 MCP 部署而暴露公网。
- IP 策略由网络入口和应用系统共同执行：防火墙/WAF 负责粗粒度准入、恶意流量拦截和 DDoS 缓解；应用负责基于可信来源、身份、路由和风险信号的限流、攻击检测、审计及临时阻断。应用不得直接修改服务器防火墙规则。
- 系统级全局封禁优先于所有来源允许名单。公司级办公/开发 CIDR 白名单在公司详情的“安全与 IP 访问”设置维护，只适用于已认证且由后台身份绑定到该公司的会话或 MCP 客户端；MCP 请求不得通过自报参数选择公司 Scope。
- 公司白名单仅增加来源限制，不得豁免系统封禁/限流、代替认证和授权、绕过账户归属或跨租户访问。MCP 工具授权不能独立决定公司范围，后台 API 必须根据已认证主体解析公司 Scope 并逐次执行规则。公司管理员自助配置权限未经单独评审前不开放。
- 对认证、凭证/授权变更、工具调用和昂贵查询实施分层限流，结合来源 IP、客户端身份、用户、工具和全局容量；跨实例策略应一致，且限流存储失效时须有安全降级和告警。
- 可按经安全评审的阈值对高置信攻击来源实施有 TTL 的临时 IP 阻断；封禁必须可解释、可审计、可到期和人工解除，避免永久自动封禁及共享 NAT 误伤。先限速/冷却，再根据多信号决定升级，不因单次普通错误永久封禁。
- 来源 IP 仅能依据明确配置的可信代理链确定。边缘层须清除外部伪造的转发头；不得直接信任任意 `X-Forwarded-For`/`Forwarded`。覆盖 IPv4/IPv6、负载均衡和多实例，并保留受控的紧急恢复路径。
- 登录保护应结合账号和来源维度的渐进延迟/短时锁定、MFA（如启用）、凭证撤销和异常告警；认证错误不得泄露账号是否存在。工具输入须有类型/范围/长度校验及成本上限，外部行情/Broker 文本始终视为不可信内容。
- 后台 API 必须重新执行认证、权限、账户归属、风险和业务校验；MCP 工具级授权、宿主 UI、IP 允许名单都不能取代服务端授权。
- 若 QuickTrade API 前增加 BFF/SSR 或 MCP 代理层，该层不得直连数据库/券商、复制业务规则或成为任意代理；须评审令牌转发、目标限制、转发头、SSRF、CSRF、XSS、错误/日志脱敏与跨用户缓存泄漏。CORS 不是 API 鉴权，Cookie 会话要有 CSRF 防护，JWT 不提供自动防重放能力。
- 建立攻击响应能力：限制来源、撤销 MCP 凭证/会话、关闭受影响工具或写能力、保护审计证据并告警。策略阈值、时长、升级对象和响应 SLA 由安全评审及运行基线确定，不在设计阶段臆定。

## 8. 日志、审计与告警

- 使用结构化日志和 UTC 时间；MCP Server 到后台 API 贯通 `traceId`/`requestId`，记录服务/环境/版本、调用客户端/主体的内部标识、工具名、授权账户内部 ID、结果分类、错误码和耗时。
- 分清运行日志、访问日志、安全/管理审计、交易业务事件和指标。安全审计至少覆盖身份认证/授权拒绝、限流/IP 阻断、凭证撤销、工具调用结果、写操作确认与幂等结果；交易状态以后台权威记录为准。
- 日志不得记录密码、Token、密钥、完整账户凭证、完整订单请求或不必要的个人信息；参数仅记录白名单摘要或脱敏摘要。未经清理和长度限制的模型输入、工具输出和外部错误文本不得直接写入日志。
- 告警规则应覆盖异常认证/授权、攻击拦截、工具错误率/延迟、限流存储故障、审计写入中断和高风险操作；支持去重、抑制、恢复通知和处置升级，阈值由运行基线确定。
- 日志和审计按数据类别配置访问控制、保留期限、归档/删除及查询审计；不得无限期保留，也不得为排障而默认持久化完整 MCP 上下文或所有工具参数。

## 9. 数据库、持久化与保留

- MCP Server 不得直连 QuickTrade 数据库。所有业务读写经 QuickTrade API 与服务层完成，数据库授权策略和交易约束由后台执行。
- 不重复镜像 API 已提供的账户、持仓、订单或行情数据。仅在会话/幂等/撤销/审计等实现确有必要且无现存权威来源时，保存最小字段、明确数据所有者和用途，并定义 TTL/保留期限。
- 幂等与交易确认状态不得只存于易失缓存；写操作结果不确定时保留必要状态并通过后台查证，不得盲目重复调用。不得将秘密或完整模型上下文持久化。
- 数据库 schema 变化须先核验现有实体、迁移历史、索引、外键和所有消费者，再以新的向前兼容迁移实现；禁止修改已执行的迁移脚本。针对查询量、分页上限和索引做验证。
- 保留期限按数据类别由产品、合规和运维确认；过期清理须分批、可重入、可暂停、可审计、有失败告警。未完成交易、未知结果、调查保全或法律保留的数据不可按普通 TTL 清除。

## 10. UI 与确认交互原则

- MCP Host/客户端 UI 应沿用产品现有设计系统、字体层级、图标语义、布局和无障碍要求；主题/皮肤可以改变视觉风格，但不能只靠颜色传达权限、错误、订单状态或风险级别，也不能降低报价、数量、价格和警告的可读性。
- 清楚呈现加载、空数据、过期/延迟数据、无权访问、限流、网络错误、结果未知及可恢复操作；不得把错误或超时显示成成功，也不得在结果未知时自动重复交易写操作。
- 交易确认必须由受信任 UI 呈现账户、标的、方向、数量、价格、订单类型和有效期等完整参数及影响；确认动作绑定这些参数，参数变化时重新确认。不得仅用一键默认同意、模型自然语言或布尔输入代替用户确认。
- 不向界面、剪贴板或模型上下文暴露凭证；账户选择、权限和危险动作在 UI 中的限制仅为辅助，后台仍需逐次校验。
- UI 需支持键盘/辅助技术、明确焦点与可读标签；关键状态同时使用文字/图形等冗余表达，节日装饰/吉祥物不得覆盖或干扰交易关键控件。

## 11. 错误与结果格式

- 参数错误、未认证、无权访问、资源不存在、限流及 Broker 故障应转换为明确且不泄露敏感信息的工具错误。
- 工具结果优先返回稳定的结构化数据，并提供简洁的人类可读摘要；错误应区分可重试与不可重试情形。
- 返回数据不得声称超出来源数据能证明的事实。行情应带时间与时效状态；交易工具应区分“请求已受理”“订单状态已确认”和“结果未知”等状态。

## 12. 实施阶段与验收

### 阶段一：只读接入

实现 MCP 身份映射、最小权限、账户隔离、只读工具、可信来源解析、统一限流、日志/审计、脱敏和数据最小化。验证未授权调用被拒绝、不能跨账户读取、伪造转发头无效、跨实例限流、全局封禁优先于公司白名单、公司间策略隔离、临时 IP 阻断可到期/解除、审计不泄密，以及 MCP 与 UI/API 查询结果遵循相同业务模型。

### 阶段二：受控交易

在阶段一通过验收后，再单独评审交易风险并启用写权限。验收必须覆盖交易权限默认关闭、完整参数确认绑定、账户/客户端隔离、提交时重新授权、限额/价格/购买力校验、并发风险竞态、确认过期/参数变更后拒绝、重放与幂等防重、越权账户被拒绝、审计不可用时拒绝写入、紧急停止与受控恢复、撤改单及部分成交状态、结果未知状态表达、权限撤销生效及 UI 错误/加载/延迟状态。所有测试仅使用 Mock/测试环境，不连接真实账户或提交真实订单。

MCP 是可选的 AI 接入扩展；在交易安全条件未满足前，系统应保持只读，不因 MCP 接入而改变既有 UI/API 的交易行为。

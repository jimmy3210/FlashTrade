# 10-系统架构与非功能需求

## 1. 目标

本文件用于说明 QuickTrade V1 的总体系统架构、主要模块职责以及非功能需求，为后续后端与前端实现提供统一边界。

## 2. 总体架构

QuickTrade V1 采用统一后台服务架构：系统自有 UI 和其他获授权 API 消费方都调用同一套 QuickTrade API，由同一套后台服务处理业务，再由 Broker Adapter 对接券商。UI 不另行直连券商，也不配置独立后台。

```text
QuickTrade UI ─────┐
                   ├──→ QuickTrade API（认证 / 授权 / 限流）
Other API Clients ─┤                  ↓
MCP Host → MCP Server ┘
                              Service Layer
                                     ↓
                              Broker Adapter
                                     ↓
                         Schwab / Tastytrade APIs
```

MCP Server 是可选的 AI 接入层，仅将获准的工具映射到 QuickTrade API；它不直连 Broker，也不承载独立业务规则。MCP 工具分阶段开放及其安全要求见 [MCP 接入设计](18-MCP接入设计.md)。

## 3. 模块说明

### 3.1 Frontend

自有前端负责展示 UI、处理用户输入，并通过 QuickTrade API 调用后台业务能力。其他获授权的 API 消费方也通过相同 API 使用这些能力。

### 3.2 QuickTrade Service Layer

统一业务服务层，负责：

- 为自有 UI 与其他 API 消费方提供统一接口
- 组合多个业务能力
- 处理业务规则与状态流转

API 入口在调用业务服务前执行身份认证、权限与账户范围校验，并实施分层请求限制；这属于同一套后台的 API 访问控制，不为 UI 或外部调用方另建后台。

### 3.3 Broker Adapter Layer

Adapter 层负责：

- 适配不同 Broker 的接口格式
- 进行字段映射与类型转换
- 封装 Broker 的异常和调用差异

### 3.4 Broker API

底层实际数据来源，包括：

- Schwab API
- Tastytrade API

## 4. 核心业务流

### 4.1 登录与初始化

```text
用户登录 → 建立 Broker 会话 → 加载账户信息 → 初始化 WatchList / Quote 状态
```

### 4.2 查看行情

```text
用户选择股票 → 调用 Quote Service → 通过 Adapter 获取 Broker 行情 → 返回 UI
```

### 4.3 提交订单

```text
用户输入买卖参数 → 校验 → 调用 Order Service → Adapter 提交订单 → 返回订单结果
```

### 4.4 查看持仓与账户

```text
调用 Position / Account Service → 通过 Adapter 获取 Broker 数据 → 展示到 UI
```

## 5. 非功能需求

### 5.1 性能

- 行情查询应在可接受延迟内返回
- 页面刷新频率满足 V1 体验要求
- 订单相关操作应尽量保证及时反馈

### 5.2 可用性

- 系统应在 Broker 调用失败时给出明确提示
- 关键操作应具备重试或降级策略
- 用户应能看到当前连接状态

### 5.3 可扩展性

- 新增 Broker 时，只需新增 Adapter，不需要重写 UI 或核心业务逻辑
- 服务层接口应保持稳定

### 5.4 可维护性

- 模块职责明确，避免业务逻辑散落在 UI 层
- 统一字段模型和接口格式，便于维护和测试

### 5.5 安全性

- 账户凭证应安全存储与传输
- UI 用户与外部 API 客户端应采用可区分、可撤销的身份凭证，并按最小权限原则授权
- 每个请求均校验操作权限及用户、客户端与目标账户的访问关系
- 按客户端、用户、账户和接口成本实施可配置的频率限制、周期配额与并发限制；超限返回 `429`，适用时提供 `Retry-After`
- 多实例部署时通过 Redis 等共享设施协调限流状态，避免实例之间额度不一致
- 下单等交易请求应校验参数与账户状态，使用幂等键避免重试导致重复下单，并记录审计日志
- 避免将 Broker 密钥直接暴露给前端
- 凭证、密钥和敏感账户数据不得写入普通日志
- 可选 MCP 接入应采用只读优先、最小权限；交易写操作默认关闭，只有在受信任确认、幂等和审计机制通过验收后才可启用

## 6. 设计约束

- V1 不引入复杂分析能力
- V1 优先保证核心交易闭环
- 不依赖第三方历史行情数据
- Broker 相关差异必须通过 Adapter 层封装

## 7. 总结

QuickTrade V1 的架构目标不是“做出一个功能最全的平台”，而是建立一个由自有 UI 和统一 API 共同访问的后台系统，提供稳定的核心交易能力，并便于接入不同 Broker。

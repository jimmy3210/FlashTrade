# 10-系统架构与非功能需求

## 1. 目标

本文件用于说明 QuickTrade V1 的总体系统架构、主要模块职责以及非功能需求，为后续后端与前端实现提供统一边界。

## 2. 总体架构

QuickTrade V1 建议采用分层架构，职责清晰，便于扩展和替换 Broker。

```text
Frontend / UI
    ↓
QuickTrade Service Layer
    ↓
Broker Adapter Layer
    ↓
Schwab / Tastytrade API
```

## 3. 模块说明

### 3.1 Frontend

前端负责展示 UI、处理用户输入、调用 QuickTrade 服务接口。

### 3.2 QuickTrade Service Layer

统一业务服务层，负责：

- 统一对外接口
- 组合多个业务能力
- 处理业务规则与状态流转

### 3.3 Broker Adapter Layer

Adapter 层负责：

- 适配不同 Broker 的接口格式
- 进行字段映射与类型转换
- 封装 Broker 的异常和调用差异

### 3.4 Broker API

底层实际数据来源，包括：

- Schwab API
- Tastytrade API

## 4. 核心业务流

### 4.1 登录与初始化

```text
用户登录 → 建立 Broker 会话 → 加载账户信息 → 初始化 WatchList / Quote 状态
```

### 4.2 查看行情

```text
用户选择股票 → 调用 Quote Service → 通过 Adapter 获取 Broker 行情 → 返回 UI
```

### 4.3 提交订单

```text
用户输入买卖参数 → 校验 → 调用 Order Service → Adapter 提交订单 → 返回订单结果
```

### 4.4 查看持仓与账户

```text
调用 Position / Account Service → 通过 Adapter 获取 Broker 数据 → 展示到 UI
```

## 5. 非功能需求

### 5.1 性能

- 行情查询应在可接受延迟内返回
- 页面刷新频率满足 V1 体验要求
- 订单相关操作应尽量保证及时反馈

### 5.2 可用性

- 系统应在 Broker 调用失败时给出明确提示
- 关键操作应具备重试或降级策略
- 用户应能看到当前连接状态

### 5.3 可扩展性

- 新增 Broker 时，只需新增 Adapter，不需要重写 UI 或核心业务逻辑
- 服务层接口应保持稳定

### 5.4 可维护性

- 模块职责明确，避免业务逻辑散落在 UI 层
- 统一字段模型和接口格式，便于维护和测试

### 5.5 安全性

- 账户凭证应安全存储与传输
- 交易请求应有必要的鉴权与校验
- 避免将 Broker 密钥直接暴露给前端

## 6. 设计约束

- V1 不引入复杂分析能力
- V1 优先保证核心交易闭环
- 不依赖第三方历史行情数据
- Broker 相关差异必须通过 Adapter 层封装

## 7. 总结

QuickTrade V1 的架构目标不是“做出一个功能最全的平台”，而是建立一个“核心交易能力稳定、可扩展、便于接入不同 Broker 的基础框架”。

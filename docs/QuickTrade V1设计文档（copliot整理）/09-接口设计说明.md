# 09-接口设计说明

## 1. 目标

本文件用于定义 QuickTrade V1 对 UI 和其他获授权 API 消费方提供的统一 API 契约。系统自有 UI 的交易与查询也调用这套 API；UI 与其他消费方共用同一套后台服务，不另设一套 UI 专属后台。后端内部再通过 Adapter 对接券商 API。

## 2. 接口设计原则

- 自有 UI 和其他 API 消费方均通过 QuickTrade API 访问业务能力，不直接调用 Broker 原始接口
- UI 和其他消费方共用同一套后端服务
- 所有接口返回统一格式，便于前端统一处理
- Broker 相关差异由 Adapter 层处理
- 接口命名要简洁、稳定、便于扩展

## 2.1 认证、授权与请求限制

- 所有业务 API（登录、令牌刷新等认证入口除外）必须先完成身份认证。V1 仅纳入 UI 用户会话；独立外部 API 客户端凭证不纳入首发，按阶段 8 单独评估。
- 如后续批准外部 API 客户端接入，须使用可区分、可撤销的独立身份凭证，并按授权范围访问获准的用户或账户；不得共用或暴露券商凭证。凭证须支持撤销和轮换，传输与存储应采取保护措施，禁止写入普通日志。
- 每次请求都要执行授权校验，至少校验操作权限及用户、客户端与目标账户之间的访问关系；不能仅依赖客户端传入的账户 ID。
- 请求数限制按客户端、用户和账户分层实施，并可按接口成本区分行情查询、账户查询和交易操作；另可配置周期性配额及并发上限。限制值应结合券商 API 限额、部署容量和运行监控确定，不在设计阶段固定未经验证的数值。
- 超出频率限制或配额时返回 HTTP `429 Too Many Requests`，并在适用时通过 `Retry-After` 告知可重试时间。限流状态应覆盖所有服务实例；多实例部署时使用 Redis 等共享存储或等效的集中式限流设施。
- 下单接口应支持幂等键，防止客户端因超时重试而重复创建订单；服务端应校验订单权限、账户状态和请求参数，并记录关键交易操作的审计信息。
- MCP 是可选的 AI 工具接入层；MCP Server 只能调用本文件定义的 QuickTrade API，不得直连 Broker 或绕过 API 的认证、授权、限流和业务校验。MCP 工具、身份映射及交易确认边界详见 [MCP 接入设计](18-MCP接入设计.md)。

## 3. 统一响应格式

V1 已确认采用统一响应结构（2026-11-20）：

```json
{
  "code": "SUCCESS",
  "message": "请求处理成功",
  "data": {}
}
```

### 3.1 响应字段说明

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | string | 稳定的业务码；成功码为 `SUCCESS`，错误码注册表及 HTTP 映射已由阶段 1 冻结 |
| message | string | 响应说明 |
| data | JSON 值 | 成功时为接口数据；错误时为包含字段错误和可用 trace ID 的结构化对象 |

HTTP 状态码独立表达协议状态，不复用响应体 `code`。后端包装 DTO、全局异常、Security/FIX 错误出口及 Flutter/Web 解析已迁移到该格式；错误 `data` 包含 `fieldErrors` 和服务端生成或验证的 `traceId`。业务码注册表和 HTTP 状态映射已冻结。定向测试通过；完整 API 回归和已部署调用方升级仍待验收。

错误响应示例：

```http
HTTP/1.1 400 Bad Request
```

```json
{
  "code": "VALIDATION_ERROR",
  "message": "请求参数校验失败",
  "data": {
    "fieldErrors": [
      {
        "field": "email",
        "code": "INVALID_FORMAT",
        "message": "请输入有效的邮箱地址"
      }
    ],
    "traceId": "01J..."
  }
}
```

## 4. 接口清单

### 4.1 用户与会话

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/v1/auth/login` | POST | 用户名/密码登录 |
| `/api/v1/auth/refresh` | POST | 轮换并返回新的 Access Token 与 Refresh Token |
| `/api/v1/auth/me` | GET | 查询当前会话身份 |
| `/api/v1/auth/logout` | POST | 撤销当前 Access Token；可选提交同主体 Refresh Token 一并撤销 |

### 4.2 行情

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/v1/stocks/search?query={query}` | GET | 搜索股票白名单 |
| 尚未实现 | GET | 单标的实时行情、市场状态及数据时间查询；不得以静态值冒充报价 |

### 4.3 订单

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/v1/trade/order?accountId={accountId}` | POST | 提交订单（带 `clientOrderId` 幂等键） |
| `/api/v1/trade/order/{externalOrderId}/status?accountId={accountId}` | GET | 查询券商侧订单状态 |
| `/api/v1/trade/order/{externalOrderId}?accountId={accountId}` | DELETE | 撤销订单 |
| `/api/v1/orders` | GET | 查询当前用户订单列表 |
| `/api/v1/trades` | GET | 查询当前用户成交记录 |
| Later | — | 修改订单；当前接口未实现 |

### 4.4 持仓与账户

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/v1/portfolio/positions` | GET | 获取当前用户持仓，可按账户/标的筛选 |
| `/api/v1/portfolio/asset-view` | GET | 获取聚合资产视图 |
| `/api/v1/trade/current-account` | GET | 获取当前绑定账户及配置环境 |
| 尚未实现 | GET | 统一账户摘要、现金余额、购买力专用接口 |

### 4.5 自选股

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/v1/watchlist` | GET | 获取当前用户自选股列表 |
| `/api/v1/watchlist` | POST | 添加自选股 |
| `/api/v1/watchlist/{symbol}` | DELETE | 删除当前用户自选股 |

> 说明：如果当前券商支持 Watchlist API，则后端可以优先通过该券商接口同步自选股；否则由 QuickTrade 本地 `WatchListService` 提供自选股管理。
> 
> 当前已完成 Tastytrade 自选股列表后端适配，并补充了 `flash-trade-mock` 中 Tastytrade Watchlist API 的 mock 支持。

## 6. 业务码与 HTTP 状态映射（阶段 1 已冻结）

响应体 `code` 是稳定业务码；HTTP 状态独立表达协议语义。阶段 1 已冻结以下注册表：

| HTTP 状态 | 业务码 | 含义 |
| --- | --- | --- |
| 200 | `SUCCESS` | 请求成功 |
| 400 | `VALIDATION_ERROR`、`INVALID_ARGUMENT`、`INVALID_STATE`、`STOCK_NOT_FOUND`、`STOCK_NOT_WHITELISTED` | 参数/字段校验失败或当前状态不允许操作 |
| 401 | `UNAUTHORIZED`、`INVALID_CREDENTIALS`、`TOKEN_EXPIRED`、`TOKEN_INVALID`、`REFRESH_TOKEN_EXPIRED` | 未认证或会话失效 |
| 403 | `ACCESS_DENIED`、`ACCOUNT_RISK_BLOCKED` | 角色、Scope、资源授权或风控拒绝 |
| 404 | `RESOURCE_NOT_FOUND`、`NOT_FOUND`、`ACCOUNT_NOT_FOUND` | 资源不存在 |
| 409 | `ORDER_RESULT_UNCONFIRMED` | 订单提交结果尚未确认；先查询状态，不自动重放 |
| 429 | `TOO_MANY_REQUESTS` | 请求频率/配额超限；适用时返回 `Retry-After` |
| 503 | `BROKER_UNAVAILABLE` | 券商依赖不可用；交易结果未知时不得盲目重试 |
| 500 | `INTERNAL_ERROR` | 未预期服务端错误 |

## 7. 备注

- 未来如果新增 Broker，只需要在 Adapter 层新增实现，接口层保持不变
- 前端对接口的依赖应该建立在 QuickTrade 的统一接口之上
- 所有关键交易动作都需要记录日志与异常信息
- 错误响应应避免泄露访问凭证、券商密钥或其他敏感信息

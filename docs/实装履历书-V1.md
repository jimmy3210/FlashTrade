## 技术详述

### 问题模式：文件损坏的三大表现

#### 模式 1：重复类定义（Duplicate Definition）
```dart
// 第293行
class _WindowControls extends StatefulWidget { ... }

// 第570行 - 完全重复！
class _WindowControls extends StatefulWidget { ... }
```
**根本原因**：代码合并错误或编辑器缓存同步失败

**修复方法**：选择版本号更大的定义（通常是后者），删除旧版本

#### 模式 2：孤立代码段（Orphaned Code Block）
```dart
// 第493行：某个class关闭
}

// 第494-569行：孤立的UI构建代码
          Expanded(
            child: Text(
              price,
              style: const TextStyle(color: AppColors.textPrimary),
            ),
          ),
          // ... 更多UI代码

// 第570行：又开始了新的class定义
class _WindowControls extends StatefulWidget { ... }
```
**根本原因**：粘贴/删除操作不完整，或自动修复工具执行到一半中断

**修复方法**：通过逻辑分析确定代码属于哪个上下文，若无法确定则删除

#### 模式 3：导入不完整（Incomplete Imports）
```dart
// 使用了 OrderResponse，但没导入
final ordersAsync = ref.watch(ordersProvider);  // 返回 List<OrderResponse>

// 但导入中缺少 models.dart
import '../../features/orders/providers/orders_provider.dart';  // 只导入provider
```
**根本原因**：provider 定义了类型别名但使用者忘记导入源头的数据模型

**修复方法**：跟踪类型定义源头，补充缺失的导入

## 关键设计决策

### 决策 1：删除 vs 修复损坏代码

**方案 A**：尝试修复每一处损坏
- 成本：高（逐行诊断）
- 风险：易遗漏，修复不彻底

**方案 B**：删除整个损坏段，保留清晰部分
- 成本：低（一次性删除）
- 风险：可能误删有用代码（但 Subagent 可恢复）
- ✅ **采纳**：确定第494-771行是孤立的，直接删除

### 决策 2：Subagent vs 手工编码

**方案 A**：手工逐一修复每个类定义
- 成本：极高（7个类×50行≈350行）
- 易错：容易出现签名不匹配

**方案 B**：使用 Subagent 自动生成
- 成本：低（一次Subagent调用）
- 准确：AI理解上下文，签名匹配度高
- ✅ **采纳**：调用Subagent生成所有Helper Widget类

### 决策 3：null-safety 处理风格

**问题**：`OrderResponse` 是否可为 null？

**选择**：使用 `order?.symbol ?? '-'` 防御性编程
- 原因：数据来自异步provider，加载阶段可能为空
- 权衡：会产生"不必要的null-aware"警告，但运行时安全
